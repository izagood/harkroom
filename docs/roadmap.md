# 실사용까지의 로드맵

- 기준일: 2026-09-01 (저녁)
- 기준 커밋: `main` (PR #26~#71 머지 후)
- 이 문서의 성격: [`design.md`](design.md)가 **무엇을 만들 것인가**라면, 이 문서는
  **지금 어디까지 왔고 실사용까지 무엇이 남았는가**다. 아래 항목은 전부 코드로 확인했고,
  확인하지 못한 것은 §5에 따로 적었다.

## 1. 지금 동작하는 것

실측(로컬 스택 기동 + 실앱 조작 + 실제 에이전트 런타임 연결)으로 확인된 범위:

- 인증 — 부트스트랩, 초대 가입, 로그인, 에이전트 PAT
- 채널 / 스레드 / DM, 멘션 → inbox
- WS 실시간 — `message.created` `message.updated` `message.deleted` `inbox.updated`
  `lease.changed` `reaction.added` `reaction.removed`, presence 스냅샷·전이(다중 소켓
  refcount 게이팅), 하트비트 기반 죽은 연결 정리
- **avcs 투영 루프 end-to-end** — 실제 `@izagood/avcs-server`에
  intent → session → lease → operation ×3 → evidence → decision → lease 반납을 넣고,
  채널에 시스템 메시지가 스레드 귀속까지 맞게 투영되고 작업 현황판에 lease가 뜨는 것 확인
- **에이전트 런타임 end-to-end** — `packages/agent`가 MCP로 붙어 멘션에 답한다. UI로 만든
  에이전트가 UI에 입력한 지시문대로 답하고, 지시문을 고치면 **러너를 재시작하지 않고** 다음
  답변부터 반영된다(`GET /agent/config`를 답변마다 읽는다)
- **UI로 에이전트 등록·수정** — 이름·지시문·harness·모델·effort·작업 디렉터리. PAT는 생성
  시 한 번만 보인다
- Tauri 데스크탑 3컬럼 UI, 세션 복원, WS 재연결, 자격증명 만료 안내
- MCP 도구 9종 — `workspace.guide` `account.me` `channel.list` `message.read`
  `message.search` `message.post` `inbox.poll` `inbox.read` `work.link`
- 이모지 리액션 — 누가 눌렀는지까지. 마지막 사람이 떼면 칩이 사라진다
- 파일·이미지 첨부 — 이미지는 미리 보인다. 업로드가 메시지보다 먼저 존재하고, 각 업로드
  안에서 파일을 먼저 쓰고 DB 행을 나중에 만든다(되돌릴 수 있는 실패를 고른다)
- 읽음 위치 — "여기부터 안 읽음" 구분선과 채널별 미읽음 수
- 타이핑 표시 — 누가 입력 중인지. 소켓의 방향을 처음 뒤집은 기능이다
- @멘션 자동완성과 강조 — 서버의 알림 발송과 **같은 규칙**을 읽는다(갈라지면 강조되지 않은
  것이 몰래 알림을 보내거나, 강조된 것이 알림을 보내지 않는다)
- 멘션 고정 — 한 번 부른 상대를 그 대화(채널/스레드)에서 유지한다. 매번 다시 치게 하면
  사람은 잊고, 잊으면 에이전트는 깨어나지 않는다
- 감사 추적(append-only), 메트릭 엔드포인트, 로그인·가입·티켓 레이트 리밋
- 테스트 536건(desktop 235 + server 272 + agent 29), PR·main 푸시에 CI 게이트

## 2. 실사용까지 남은 것

"실사용"의 층이 셋이고, 층마다 성격이 다르다.

### 층 1 — 1인 도그푸딩에서 바로 물리는 것 — **완료**

| 항목 | 결과 |
|---|---|
| 메시지 수정/삭제 | `PATCH`/`DELETE` + `message.updated`/`deleted` 푸시. 수정은 작성자만, 삭제는 작성자 또는 admin(서버가 열어 둔 조정 수단이 UI에서 도달 가능해야 한다). 본문은 감사에 복사하지 않는다 — 복사하면 삭제가 삭제가 아니다 |
| 과거 메시지 스크롤 | `before` 커서(역방향 페이지: desc로 잡아 오름차순으로 되돌린다) + `hasMore` + "Load older" |
| OS 알림 | 멘션 도착 시 알림. 포커스가 있으면 띄우지 않고, 항목당 한 번만, 기동 시 백로그는 억제한다 |
| PAT 폐기가 실시간 접근을 못 끊음 | 60초 재검증 sweep이 살아 있는 해시 전체를 **한 번의 질의**로 판정하고 무효면 4401로 끊는다. 같은 자격증명의 소켓들이 운명을 공유한다("어떤 탭은 끊기고 어떤 탭은 사는" 상태 방지). 클라이언트는 4401·티켓 401을 네트워크 장애와 구분해 재시도를 멈추고 재로그인을 안내한다 |

층 1에서 추가로 닫은 것: 접근성(호버 전용 버튼을 `visibility` 대신 `opacity`로 숨긴다 —
`visibility:hidden`은 접근성 트리에서 요소를 지워 키보드 경로를 없앤다), idempotency 키
스코핑(`(author_id, channel_id, key)` — 전역 키는 남의 메시지를 읽는 경로였다), WS 티켓
인증(30초 TTL·1회용), Origin 허용 목록(`tauri build` 산출물의 실제 Origin을 **측정한 뒤**
좁혔다), 멘션 규칙 통일(서버의 알림 발송과 UI의 강조가 같은 규칙을 읽는다).

### 층 2 — 며칠 쓰면 반드시 부딪히는 것 — 기능은 닫혔고 하나 남았다

| 항목 | 결과 |
|---|---|
| 파일·이미지 첨부 | `StorageBackend` 뒤에 로컬 볼륨(S3 는 그 파일만 갈아 끼우면 된다). 업로드가 메시지보다 먼저 존재하고, 각 업로드 안에서 **파일을 먼저 쓰고 DB 행을 나중에** 만든다 — 실패했을 때 남는 것이 고아 파일이라 GC 로 치울 수 있고, 반대 순서는 가리키는 파일이 없는 행을 남긴다. 절단 업로드를 거절한다(파서가 제한에서 스트림을 조용히 잘라내는데, 그걸 성공으로 저장하면 제한이 없는 것보다 나쁘다). 미리보기는 화이트리스트 — SVG 는 스크립트를 담고 파일명은 올린 사람이 정한다 |
| 읽음 위치 | `channel_read(account, channel → last_read_seq)`. SQL 이 두 성질을 강제한다 — 되돌아가지 않고(`greatest`), 채널 끝을 넘지 않는다(`least`). 후자가 더 위험하다: 되돌아가는 건 눈에 보이지만 놓치는 건 안 보인다. 구분선은 채널을 **열 때**의 위치로 고정한다 |
| 타이핑 표시 | 클라이언트 → 서버 소켓 메시지. 만료가 핵심이다 — 탭을 닫으면 stop 이 오지 않으므로 TTL 6초 + close 정리 + 3초 갱신으로 세 겹이다. 이벤트는 상태 전체를 보내고(`typing.changed`), 자기 자신은 **서버가** 뺀다 |
| 리액션 | 이모지 리액션 + 누가 눌렀는지. 서버가 받아들인 뒤에만 화면이 바뀐다 — 미리 그리면 서버가 거절한 것이 새로고침에서 사라져 사용자가 무엇이 진짜인지 알 수 없다 |
| presence 정확도 | 하트비트 도입. 직전 ping에 pong이 없으면 끊는다 — 케이블이 뽑히거나 피어가 wedge되면 close 이벤트가 오지 않아 죽은 연결이 online으로 남았다 |

층 2 에서 남은 것은 하나다:

| 항목 | 현황 |
|---|---|
| **서버 재시작 = 전원 끊김** | **여전하다.** 인메모리 상태 5종(이벤트 버스·presence 카운터·WS 티켓·타이핑 상태·레이트 리밋 카운터)이 재시작에서 사라진다. 다만 SIGTERM drain이 있어 진행 중인 `inbox.poll`은 빈 결과로 정상 마감되고 러너는 백오프로 이어붙는다. 이것은 §2 층 3 의 '수평 확장 불가'와 **같은 뿌리**다 — 인메모리 상태를 밖으로 빼면 둘이 함께 풀린다 |

### 층 3 — 팀에 배포하려면

| 항목 | 현황 |
|---|---|
| 관측 | 감사 추적(누가 무엇을 바꿨는지 append-only)과 메트릭 엔드포인트 도입. 투영이 조용히 멈춘 것이 숫자로 보인다 |
| 레이트 리밋 | 로그인·가입·티켓 발급에 있다. **메시지 게시·리액션·업로드 등 일반 경로에는 없다** — 업로드는 25MB 제한만 있어 반복 업로드로 디스크를 채울 수 있다 |
| **수평 확장 불가** | 인메모리 상태 **5종** 때문에 인스턴스가 1개여야 한다 — 이벤트 버스 · presence 카운터 · WS 티켓 · 타이핑 상태 · 레이트 리밋 카운터. `design.md` §3이 명시한 전제이지만 규모가 커지면 제약이다. 층 2 의 '서버 재시작 = 전원 끊김'과 같은 뿌리다.<br><br>다섯 중 **레이트 리밋 카운터는 성질이 다르다** — 잃으면 리밋이 리셋될 뿐 사용자에게 보이는 상태가 사라지지 않는다. 반면 수평 확장에서는 오히려 더 위험하다: 인스턴스마다 카운터가 따로면 허용량이 인스턴스 수만큼 곱해진다. 우선순위를 매길 때 이 차이가 쓸모 있다 |
| 백업·복구 | 절차는 `operations.md`에 있고, 래퍼 스크립트(`status`/`logs`/`backup`/`restore`/`upgrade`)가 진행 중. **첨부가 들어오면서 백업이 둘이 됐다** — 파일 볼륨을 먼저 뜬 다음 DB 를 떠야 한다. 반대 순서면 행이 가리키는 파일이 백업에 없어 복구 후 '깨진 첨부'가 되고, 볼륨을 먼저 뜨면 그 사이 생긴 파일이 DB 에 없을 뿐이라 무해하다 |
| **데스크탑 릴리스 파이프라인 없음** | `tauri.conf.json`의 번들 설정은 `{"active": true, "targets": "all"}`뿐이고 서명·공증·자동 업데이트 설정이 없다. CI에도 릴리스 잡이 없다 |
| **토큰 평문 보관** | localStorage. `TokenStore` 인터페이스 뒤에 격리돼 교체는 쉽지만 Tauri 공식 키체인 플러그인 부재로 미해결 |
| 에이전트 러너 감독 | **닫혔다(로컬).** 러너는 손으로 띄운 프로세스였고 죽으면 아무도 몰랐다 — **2026-09-01 저녁에 실제로 일어났다.** 사용자가 `@fizz` 를 두 번 불렀는데 답이 없었고, 원인은 기능이 아니라 러너가 죽어 있던 것이었다. 서버·메트릭은 정상이었고 `inbox` 에 미처리 항목이 쌓이는 것만 보였다. at-least-once 설계 덕에 다시 띄우자 밀린 부름을 처리했지만 20분 늦었다.<br><br>지금은 launchd LaunchAgent(`~/Library/LaunchAgents/dev.murmur.agent.fizz.plist`)가 `KeepAlive` 로 지켜본다. `kill -9` 로 검증했다. 두 가지가 함정이었다: **`pnpm` 을 거치면** 감독 대상이 pnpm 이 되어 러너가 죽어도 살아 있는 경우가 생기므로 `tsx` 를 직접 부른다. **launchd 는 로그인 셸의 PATH 를 물려받지 않으므로** `PATH` 를 명시해야 `claude` 를 찾는다 — 이것이 조용한 실패의 흔한 원인이다.<br><br>남은 것: 배포 대상 머신마다 이 파일을 만드는 절차(리눅스는 systemd 유닛), 그리고 러너를 여럿 띄울 때의 관리. 감독은 프로세스 죽음만 막으므로, 러너가 **살아 있으면서 일을 못 하는** 경우(자격증명 만료·서버 접속 실패)는 메트릭이 잡는다 |

## 5. 아직 확인하지 못한 것

아래는 "없다"가 아니라 **"돌려보지 않았다"**이다. 여기서 나올 결함이 §2 목록보다 근본적일 수
있다.

- **`work.link`** — 도구는 등록돼 있으나 intent ↔ 스레드 승격을 end-to-end로 확인하지 않았다
- **`/search` 품질** — 라우트가 있고 테스트가 통과한다는 것까지만 안다. 한국어 형태소 분석 없이
  `to_tsvector('simple', ...)`을 쓰므로 조사가 붙은 검색어의 재현율을 재 본 적이 없다
- **투영 규모** — repo 1개 · 채널 1개 · 객체 20여 개 수준에서만 확인했다
- **에이전트 여러 대 동시 운영** — `design.md` §8이 요구하는 "에이전트 2개 이상이 한 채널에
  참여"는 계정·PAT 수준에서는 되지만, 러너 2대를 동시에 띄워 같은 멘션에 경합하는 상황을
  돌려본 적이 없다
- **러너가 오래 도는 것** — 지금까지 확인한 것은 "띄우면 답한다"이고, 며칠 연속으로 도는 동안
  자격증명 만료·메모리·좀비 `claude` 프로세스가 어떻게 되는지는 모른다. 층 3 의 러너 감독
  항목과 같은 뿌리다
- **harness 다양성** — `claude-code` 하나만 구현했다. UI의 나머지 선택지는 '지원 예정'으로
  비활성이며, 그것들을 붙일 때 `buildClaudeArgs` 상당의 어댑터가 harness마다 필요한지
  아니면 공통 형태로 수렴하는지 모른다

## 6. 최근에 닫은 결함 중 기록해 둘 것

**가드 없는 `pg.Pool` — Postgres 재시작이 곧 서버 사망이었다.** CI가 간헐적으로 빨갰고
(`57P01 terminating connection due to administrator command`가 unhandled error로 샜다)
처음에는 "testcontainer 정리 경합, 테스트 환경 문제"로 읽혔다. 실제 원인은 프로덕션
결함이었다 — `pg`는 유휴 클라이언트 에러를 Pool이 대신 emit하고 **리스너가 없으면 uncaught
exception으로 던진다.** Postgres가 재시작하면(compose restart·failover·OOM) 살아 있는 유휴
연결에 FATAL이 오고 그 순간 서버 프로세스가 죽었다. DB는 돌아오는데 서버는 안 돌아오는
형태이며, §2의 SIGTERM drain으로 만들어 둔 재시작 내성과 정면으로 어긋났다.

지금은 `createPool()`이 Pool을 만드는 유일한 지점이고 생성과 가드를 한 함수에 묶었다 —
가드 없는 Pool이 생길 수 있는 자리를 없애는 것이 리스너를 하나 더 붙이는 것보다 확실하다.

**남길 교훈**: "테스트에서만 나고 로컬에서는 재현되지 않는다"를 테스트 환경 문제로 치부하면
그 아래의 프로덕션 결함을 놓친다. 재실행하면 통과한다는 사실이 무해함의 근거가 아니다.
