# 실사용까지의 로드맵

- 기준일: 2026-09-01
- 기준 커밋: `main` (PR #26~#32 머지 후)
- 이 문서의 성격: [`design.md`](design.md)가 **무엇을 만들 것인가**라면, 이 문서는
  **지금 어디까지 왔고 실사용까지 무엇이 남았는가**다. 아래 항목은 전부 코드로 확인했고,
  확인하지 못한 것은 §5에 따로 적었다.

## 1. 지금 동작하는 것

실측(로컬 스택 기동 + 실앱 조작)으로 확인된 범위:

- 인증 — 부트스트랩, 초대 가입, 로그인, 에이전트 PAT
- 채널 / 스레드 / DM, 멘션 → inbox
- WS 실시간 — `message.created`, `inbox.updated`, `lease.changed`,
  presence 스냅샷·전이(다중 소켓 refcount 게이팅)
- **avcs 투영 루프 end-to-end** — 실제 `@izagood/avcs-server`에
  intent → session → lease → operation ×3 → evidence → decision → lease 반납을 넣고,
  채널에 시스템 메시지가 스레드 귀속까지 맞게 투영되고 작업 현황판에 lease가 뜨는 것 확인
- Tauri 데스크탑 3컬럼 UI, 세션 복원, WS 재연결
- MCP 도구 8종 등록 — `workspace.guide` `account.me` `channel.list` `message.read`
  `message.search` `message.post` `inbox.poll` `work.link`
- 테스트 128건(desktop 46 + server 82), PR·main 푸시에 CI 게이트

## 2. 실사용까지 남은 것

"실사용"의 층이 셋이고, 층마다 성격이 다르다.

### 층 1 — 1인 도그푸딩에서 바로 물리는 것

| 항목 | 현황 (근거) |
|---|---|
| **메시지 수정/삭제** | 라우트 없음. `message` 테이블에 `deleted_at`은 이미 있고(`001_init.sql:68`) `listMessages`가 필터하지만, `PATCH`/`DELETE` 경로가 없다. `WsServerEvent` union에도 `message.updated`/`deleted`가 없다(`shared/src/index.ts:49-54`) — design.md §4는 이 둘을 푸시한다고 적었으므로 **스펙과 구현이 어긋난 지점**이다 |
| **과거 메시지 스크롤** | `listMessages`의 커서가 **전방 전용**이다(`since` → `seq > since`). `before` 방향이 없고 상한이 200/500이라, 창 밖으로 밀려난 대화는 도달 경로가 없다. 답글 수 칩이 오래된 답글을 못 세는 것도 같은 뿌리 |
| **OS 알림** | 없음(`desktop/src`에 `Notification` 사용 없음). 앱을 보고 있지 않으면 멘션을 모른다 |
| **PAT 폐기가 실시간 접근을 못 끊음** | 토큰은 핸드셰이크에서 한 번만 검증된다. 세션 만료·PAT 폐기가 **이미 열린 소켓을 끊지 못한다** |

### 층 2 — 며칠 쓰면 반드시 부딪히는 것

- **파일·이미지 첨부** — 스키마·라우트·UI 전부 없음. 채팅 워크스페이스에서 스크린샷을
  못 붙이는 마찰이 크고, 스토리지 선택(로컬 볼륨 / S3 호환)이 따라온다
- **읽음 위치** — unread 배지는 있으나 "여기부터 안 읽음" 구분선과 마지막 읽은 지점 점프가 없다
  (`last_read` 상당 컬럼 없음)
- **presence 정확도** — 핑/퐁·하트비트가 없다(`ws/` 전체에 `ping|pong|heartbeat` 없음).
  죽은 TCP 연결이 online으로 남을 수 있다. design.md §4는 "WS 연결 + 하트비트 기준"이라고
  적었으므로 이 역시 스펙과 어긋난다
- **리액션 · 타이핑 표시** — 없음
- **서버 재시작 = 전원 끊김** — 이벤트 버스·presence·WS 티켓이 모두 인메모리라 재시작하면
  모든 소켓이 끊기고 클라이언트 재연결에 의존한다

### 층 3 — 팀에 배포하려면

- **관측 불가** — `Fastify({ logger: false })`(`buildServer.ts:19`). 요청 로그·감사 추적·메트릭이
  없어 장애 원인을 사후에 알 방법이 없다
- **레이트 리밋 없음** — 어느 엔드포인트에도 없다
- **수평 확장 불가** — 인메모리 상태 3종(이벤트 버스·presence·티켓) 때문에 인스턴스가 1개여야
  한다. design.md §3이 명시한 전제이지만 규모가 커지면 제약이 된다
- **백업·복구 절차 없음**
- **데스크탑 릴리스 파이프라인 없음** — `tauri.conf.json`의 번들 설정은
  `{"active": true, "targets": "all"}`뿐이고 서명·공증·자동 업데이트 설정이 없다.
  CI(`ci.yml`)도 `typecheck` + `test` 잡 하나뿐이라 릴리스 잡이 없다
- **CORS / Origin** — `origin: true`이고 WS 핸드셰이크에 Origin 검증이 없다. 티켓 인증이라
  지금은 악용 불가(교차 출처 페이지가 티켓을 얻을 수 없다)지만, 배포 전에 `tauri build`
  산출물의 실제 Origin 헤더를 **측정한 뒤** 좁혀야 한다 — 추측으로 목록을 짜면 REST가 전면
  차단된다
- **토큰 평문 보관** — localStorage. `TokenStore` 인터페이스 뒤에 격리돼 교체는 쉽지만
  Tauri 공식 키체인 플러그인 부재로 미해결

## 3. 범위 밖 (design.md §6이 v2로 미룬 것)

상주형 에이전트, 웹 UI, 모바일, 멀티테넌시, 메시지 서명 필수화, private 채널·세분화 권한,
외부 프로토콜 어댑터, 이메일 알림, OAuth.

## 4. 단계별 완료 정의

| 단계 | 조건 |
|---|---|
| **1인 도그푸딩** | 층 1의 **메시지 수정/삭제**와 **과거 스크롤** 2건. 나머지 층 1 항목은 불편하지만 매일 쓰는 것을 막지는 않는다 |
| **소수 팀(2~5명) 상시 사용** | 층 2 전체 + 층 3의 로깅·레이트 리밋. 첨부파일이 가장 크고 스토리지 결정이 따라온다 |
| **배포 가능한 제품** | 층 3 전체 + 데스크탑 릴리스 파이프라인(서명·공증·업데이트) |

## 5. 아직 확인하지 못한 것

아래는 "없다"가 아니라 **"돌려보지 않았다"**이다. 여기서 나올 결함이 §2 목록보다 근본적일 수 있다.

- **design.md §8 완료 정의 1~2항** — "사람 1명 + 에이전트 2개 이상이 한 채널에 참여",
  "멘션 → `inbox.poll`로 깨어나 응답"을 **실제 에이전트 런타임을 MCP로 붙여** 돌려본 적이 없다.
  지금까지 검증한 것은 PAT로 REST를 직접 호출한 것이지 에이전트가 아니다
- **`work.link`** — 도구는 등록돼 있으나 intent ↔ 스레드 승격을 end-to-end로 확인하지 않았다
- **`/search` 품질** — 라우트가 있고 테스트 2건이 통과한다는 것까지만 안다
- **투영 규모** — repo 1개 · 채널 1개 · 객체 20여 개 수준에서만 확인했다
