# murmur 리디자인·리팩토링 — 단계 계획

> **이 문서는 순서와 경계만 정한다.** 단계별 태스크 계획서(`- [ ]` 단위)는 **그 단계에
> 착수할 때** 따로 쓴다. 넷을 지금 다 태스크로 펼치면 아직 하지 않은 결정을 미리 못
> 박게 되고, 앞 단계가 뒷 단계의 전제를 바꾸면 그 계획서가 조용히 거짓이 된다.

**Goal:** 기능이 컨셉에 닿은 지금, **다음 기능을 넣는 마찰**을 만드는 구조 셋을 걷어낸다 —
데스크탑 상태층의 신 객체 둘, `shared` 의 잡화점 배럴, 그리고 문서·마이그레이션의 드리프트.

**측정 시점:** `origin/main` `875fb79f` (v0.1.141), 2026-09-09.
아래 수치는 전부 그 커밋에서 센 것이다. 재검증 명령은 각 절에 적었다.

---

## 0. 고치지 않기로 한 것 — 먼저 적는다

리팩토링 계획에서 가장 비싼 실수는 **멀쩡한 것을 건드리는 것**이다. 다음은 재고 조사에서
**의도된 설계로 확인된 것**이고, 이 계획의 어느 단계도 손대지 않는다.

| 무엇 | 왜 손대지 않나 |
|---|---|
| 패키지 의존 방향 | 전부 → `shared` 단방향, `desktop` → `agent` 는 사이드카 번들 하나뿐. **순환 0.** 5패키지 모노레포에서 이것이 깨져 있지 않은 것은 운이 아니다 |
| `server` 의 층 분리 | `routes/ · services/ · ws/ · mcp/ · db/ · storage/`. 65파일 중 600줄을 넘는 것이 `messages.ts`(1434) · `channels.ts`(891) 둘뿐이다 |
| 마이그레이션 실행기 | advisory lock + 적용 장부(`schema_migrations`)로 롤링 부팅에서 구·신 인스턴스 동시 기동까지 감당한다(`db/migrate.ts`) |
| i18n 뼈대 | `satisfies Catalog` 로 키 누락이 **컴파일에서** 막히고, 복수형·자리표시자·조사 누락은 `test/i18n.test.tsx` 가 잡는다. 런타임 의존 0 |
| **규칙을 테스트로 강제하는 관행** | `accentBudget` · `colorTokens` · `focusRing` · `staleRunnerDocs` · `appTransportSecurity` … **소스를 읽어 규칙을 단언하는 테스트가 35개** 있다. 이것이 이 저장소가 린터 없이도 규칙을 지켜 온 방식이고, §단계 3 은 이것을 **대체하지 않는다** |

**`server` 는 이 계획의 대상이 아니다.** 아래 네 단계는 `shared` · `desktop` · `docs` 와
마이그레이션 파일명만 건드린다.

## 1. 실측 — 무엇이 얼마나 큰가

```
src 70,178줄 / test 88,846줄 (테스트 파일 365개)
src 중 주석 28,250줄 = 40%  →  실제 코드는 약 42k줄
```

| 패키지 | src | 파일 | 주석 비중 | test |
|---|---|---|---|---|
| desktop | 41,358 | 145 | 38% | 49,326 / 195 |
| server | 13,367 | 65 | 33% | 24,444 / 112 |
| agent | 7,807 | 27 | 50% | 10,339 / 38 |
| shared | 4,059 | 4 | 57% | 1,255 / 7 |
| daemon | 3,587 | 10 | 44% | 3,482 / 13 |

재검증:
```sh
for p in shared server desktop agent daemon; do
  find packages/$p/src -name '*.ts' -o -name '*.tsx' | xargs wc -l | tail -1
done
```

**주석 40% 는 결함이 아니라 이 저장소의 방식이다** — 무엇을 하는지가 아니라 왜 그
모양이어야 하고 그러지 않으면 무엇이 깨지는지를 적는다. 이 계획은 주석을 줄이지
않는다. 파일 크기를 이야기할 때 **줄 수와 코드량이 다르다**는 것만 기억한다:
`Sidebar.tsx` 2,028줄은 코드 약 1,250줄이다.

## 2. 단계 순서와 그 근거

순서를 정한 기준은 **"뒷 단계의 diff 를 읽을 수 있게 만드는 것이 앞"** 이다.
효과 크기 순이 아니다.

### 단계 1 — 드리프트 회수 (원래 D + E) · 위험 없음 · PR 1개

**마이그레이션 번호가 세 자리에서 겹친다.** 45개 중 `040_` · `043_` · `044_` 가
각각 둘이다. 적용은 파일명 정렬이고 장부가 이름으로 남으므로 **지금은 우연히 안전하다** —
겹친 둘 사이에 의존이 없기 때문이다. 위험은 다음에 겹칠 때다: 번호가 같으면 적용 순서가
알파벳에 걸리고, 그 사실은 어디에도 적혀 있지 않다.

- [ ] 번호 접두가 유니크함을 단언하는 테스트를 `packages/server/test/migrate.test.ts` 에 더한다
- [ ] 기존 세 쌍은 **개명하지 않는다** — 이미 적용된 DB 의 장부가 파일명으로 되어 있어
      개명은 곧 재적용이다. 단언은 "앞으로 겹치면 잡는다"로 두고, 겹친 셋은 예외 목록에
      **이유와 함께** 적는다

```sh
ls packages/server/src/db/migrations | sed 's/_.*//' | sort | uniq -d   # → 040 043 044
```

**`docs/design.md` §0 이 "표시가 필요한 자리는 지금 **하나**"라고 단언하는데 셋 더 있다.**
그 문장이 이 저장소에서 가장 비싼 종류의 거짓이다 — #371 이 바로 그것으로 깨졌고, §0 은
그 사고를 막으려고 쓰인 절이다.

- [ ] §2 monorepo 구성에 `packages/daemon` 이 없다. **4패키지로 적혀 있고 실제는 5다.**
      §1 이 `#431` 을 인용해 *"러너의 부모는 앱이 아니라 daemon"* 이라고 적어 두었는데
      그 패키지가 구성도에 없다
- [ ] §4 "에이전트 MCP 표면 — 도구 **17개**" → 실제 등록 **21개**
      (`grep -c "server.registerTool(" packages/server/src/mcp/mcpPlugin.ts`)
- [ ] `packages/desktop/src/i18n/types.ts` 가 *"정적 문자열 **277개**"* 를 근거로 i18n
      라이브러리를 안 쓴다고 판단했다. 실제 키는 **917개**다. 그 문서가 스스로 적어 둔
      재평가 조건이 *"문자열이 1000개를 넘으면 라이브러리가 이긴다"* 이므로, 숫자를
      고치는 것이 곧 그 조건에 닿았다는 신호가 된다. **판단을 뒤집지는 않는다** —
      숫자만 고치고, 1000 을 넘을 때 무엇을 다시 재는지 한 줄 남긴다
- [ ] §0 의 "지금 하나" 를 실제 수로 고친다

### 단계 2 — `shared/index.ts` 분해 (원래 B) · 동작 변화 0 · PR 1개

`packages/shared/src/index.ts` 2,433줄 한 파일에 멘션 파싱 · 퍼머링크 · 메시지 `meta`
리더(wake·ask·failure·report·model) · 알림 pref · 채널 정렬 · avcs 투영 상태 · 스킬 분류 ·
URL 프리뷰 추출 · 러너 종료 사유가 함께 있다. 서로 부르지 않는 여덟 덩어리다.

**이 패키지는 이미 답을 알고 있다.** `daemonProtocol` · `daemonEndpoint` · `claudePools`
는 이미 갈라져 서브패스로 export 되고, `daemon` 은 그것을
`@murmur/shared/daemonProtocol` 로 정확히 필요한 것만 가져간다. **`index` 만 monolith다.**

- [ ] 도메인별로 가른다: `mentions` · `permalink` · `messageMeta` · `channelPrefs` ·
      `projection` · `skills` · `linkPreview` · `runnerExit`
- [ ] **`index.ts` 는 재export 배럴로 남긴다.** 다섯 패키지가 여기에 타입체크로 묶여
      있고(`server` 32 · `desktop` 73 · `agent` 12 import), 배럴을 없애면 이 PR 이
      전 패키지의 import 를 건드리는 PR 이 된다 — 그러면 동작 변화 0 이라는 성질을
      리뷰에서 확인할 수 없다. **호출자 이전은 이 PR 이 하지 않는다**
- [ ] 검증: `packages/{shared,server,desktop,agent,daemon}` 전부 `npx tsc -p .`
      (`--noEmit` 을 붙이지 않는다 — CI 는 `tsc -p .` 이고 composite 라 검사 범위가 다르다),
      그리고 각 패키지 vitest 전량

### 단계 3 — desktop 상태층 해체 (원래 A) · 유일하게 회귀 위험이 실재한다 · PR 3개

문제는 신 객체 **둘**이다.

**`state/controller.ts` 2,272줄 · 메서드 약 120개 — 그중 `this.api.*` 호출이 114곳**이고
대부분이 한 줄 위임이다(`listAgents()` · `agentDefaults()` · `listTeams()` · `mintPat()` ·
`createInvite()` …). 엔드포인트를 하나 더할 때 `api.ts`(801줄) → `controller.ts` →
컴포넌트 **세 곳**을 고쳐야 하고, 가운데 한 곳은 아무 판단도 하지 않는다.

**`state/appStore.ts` 는 슬라이스 36개를 한 판에 얹었다** — 채팅 데이터 · 화면 선택 ·
이동 이력 · 러너 관측 · daemon 관측 · 투영 상태 · 앱 버전 · 링크 프리뷰 · 드래프트.

- [ ] **PR 3-1: 위임층 제거.** Controller 에 **상태를 실제로 바꾸는 것만** 남긴다 —
      WS 이벤트 적용(`handleEvent`) · 낙관적 갱신 · 이동(`openMessage` 한 곳으로 모으는
      성질은 그대로 지킨다) · 러너 조율 · `start`/`stop` 수명. 순수 위임은 컴포넌트가
      `api` 를 직접 부르거나 도메인 훅(`useAgents()` · `useTeams()`)이 받는다
- [ ] **PR 3-2: 스토어 도메인 슬라이스.** `chat` · `nav` · `directory` · `runner` ·
      `projection` · `prefs`. zustand 라 **스토어는 하나로 유지**하고 슬라이스 함수만
      가른다 — 스토어를 쪼개면 `setController`/`useActiveStore` 를 참조하는 테스트
      195개가 전부 흔들린다
- [ ] **PR 3-3: 디렉터리 평면 해소.** `components/` 55파일 한 겹(23.4k줄) ·
      `lib/` 44파일 한 겹. 큰 것: `settings/AgentsSettings.tsx` 2,277 ·
      `Sidebar.tsx` 2,028 · `Composer.tsx` 1,789 · `lib/runnerLauncher.ts` 1,794 ·
      `MessageItem.tsx` 1,027
- [ ] 각 PR 의 성질은 **동작 변화 0** 이다. 그것을 리뷰에서 확인할 수 있게 **PR 하나에
      한 성질만** 담는다 — 위임 제거와 슬라이스를 같은 PR 에 넣으면 diff 에서 둘을
      가를 수 없다

## 3. 전 단계 공통 제약

- **주석을 줄이지 않는다.** 파일을 가를 때 그 파일 머리의 근거 주석은 **판단이 옮겨간
  파일로 함께 옮긴다.** 근거를 남기고 코드만 옮기면 다음 사람이 같은 실수를 다시 한다
- **35개 guard 테스트를 무력화하지 않는다.** 소스를 읽어 규칙을 단언하는 테스트는 파일
  경로를 알고 있다(`readFileSync`). 파일을 옮기면 그 경로도 함께 고친다 — **테스트를
  지워서 초록으로 만들지 않는다**
- **공유 트리에서 작업하지 않는다.** `git worktree` 로 갈라서 하고, 커밋 전에
  `git status` 로 목록을 눈으로 본다(루트 `node_modules` 심링크가 `git add -A` 에
  삼켜져 CI 첫 걸음이 죽은 적이 있다 — #687)
- **머지는 사람이 한다.** main 머지가 곧 릴리스이므로(6~12분) 에이전트는 PR 까지만 만든다
- 검증은 `cd packages/<p> && npx tsc -p .` + 그 패키지 vitest **전량**.
  `packages/agent` 에는 환경 의존으로 origin/main 에서도 깨지는 테스트가 둘 있다
  (`CLAUDE_CONFIG_DIR 주입` · `폐기된 PAT`) — 그것은 이 작업이 깬 것이 아니다

## 4. 아직 결정하지 않은 것 — 사람의 판단이 필요하다

### 4-1. 기계적 검사층(린터·포매터)을 넣을지, 넣는다면 언제

루트 스크립트는 `test` · `typecheck` 둘뿐이고 eslint/biome/prettier 설정이 저장소
어디에도 없다. **처음 본 것보다 이 공백은 좁다** — 규칙은 위 35개 guard 테스트가
지키고 있고, 그것은 린터 룰보다 강하다(*"강조를 받는 것은 나를 막는 것과 주 동작
버튼 둘뿐"* 같은 규칙은 어느 린터도 표현하지 못한다).

린터가 실제로 더 주는 것은 **기계적인 층뿐**이다: 포맷 통일 · 미사용 import/변수 ·
죽은 export · `import type` 누락.

그런데 그 값을 받는 대가가 이 저장소에서 유별나게 크다:

- **포맷 일괄 적용은 158k줄을 건드리는 커밋 하나다.** 그것이 열려 있는 모든 PR 의
  diff 를 무효로 만들고, 여러 에이전트가 같은 트리에서 동시에 고치는 이 저장소에서는
  충돌이 사고 수준으로 커진다
- 즉 이것은 **기술 결정이 아니라 일정 결정**이다 — 열린 PR 이 없는 조용한 창이 필요하다

**그래서 이 문서는 단계에 넣지 않고 결정으로 남긴다.** 물어야 할 것 셋:

- [ ] 넣는가? (넣지 않는 것도 정당한 답이다 — guard 테스트가 이미 규칙을 지킨다)
- [ ] 넣는다면 포맷 규칙을 **기존 코드에 맞춰** 잡는가(일괄 재포맷 없음), 아니면
      도구 기본값에 맞춰 158k줄을 한 번 재포맷하는가
- [ ] 재포맷을 한다면 **어느 창**에서 하는가

### 4-2. 큰 설계 판단을 코드에서 문서로 올릴지 (원래 F)

`Sidebar.tsx:1509` 의 면·색 결정, `appStore.ts:17-49` 의 `teams: null` vs `[]` 판단
같은 것은 **그 파일을 여는 사람만 본다.** `docs/decisions/` 로 올리고 코드에는 포인터를
남기면 파일 분할이 쉬워지고 판단이 검색 가능해진다.

**이것은 저장소의 의도된 스타일을 바꾸는 제안이므로 이 계획에 넣지 않았다.** 대가도
분명하다: 근거가 코드에서 한 걸음 멀어지면 코드를 고치는 사람이 그것을 안 읽을 수 있고,
그 위험이 지금 방식이 존재하는 이유다.

## 5. 알고만 있을 것 (원래 G) — 지금 고치지 않는다

메시지 목록에 가상화가 없다. `ChannelPane` → `groupAgentExchanges(groupProgress(roots))`
→ `AgentExchange` → `MessageItem` 을 직접 `map` 한다. 지금 규모에서 문제가 아니고,
가상화는 **스크롤 앵커링·"읽은 지점" 구분선·`openMessage` 이동**과 정면으로 얽히므로
값을 하기 전에 넣으면 그 셋을 깨뜨린다. 채널 하나에서 `loadOlder` 를 오래 반복하면
DOM 이 무한히 자란다는 사실만 남긴다.
