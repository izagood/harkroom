협업이 자기 칸을 갖는다

avcs 로 에이전트끼리 코드를 협업하는 것이 murmur 의 전제다. 그런데 지금 화면에서 그 협업이 보이는 자리는 사이드바 하단의 파일 잠금 목록 하나뿐이고, 정작 무슨 제안이 떠 있고 무엇이 충돌했는지는 어디에도 없다.

지금

협업의 절반이 대화로 흐르고, 절반은 안 보인다

avcs 거버넌스 객체는 이미 murmur 채널로 투영되고 있다 (src/avcs/projection.ts). 실측한 매핑은 이렇다.

지금의 투영projection.ts:124~
avcs 객체murmur 에서보이는가
intent스레드 뿌리 + work_thread 매핑채널에 섞여 흐른다
operation그 스레드 아래 (배치 병합)채널에 섞여 흐른다
decision·evidence그 스레드 아래채널에 섞여 흐른다
checkpoint·release·finalize채널 바로 밑채널에 섞여 흐른다
leaseactive_lease → ACTIVE WORK유일하게 자기 자리를 가졌다

균형이 뒤집혀 있다. 협업의 본체(무엇을 제안했고 무엇이 결정됐는가)는 대화에 섞여 스크롤과 함께 지나가고, 곁가지(어느 파일이 잠겼는가)만 고정된 칸을 가졌다.

「나머지 여덟 곳」이 ACTIVE WORK 를 "설정 오류를 작업으로 그린다"고 지적했고, 「레일」이 "그 구역은 그냥 없어진다"고 적었다. 둘 다 맞지만 그 자리에 무엇이 대신 와야 하는지는 두 문서가 답하지 않았다 — 이 문서가 그 답이다.

전제

협업 칸은 avcshub 웹이 하던 일을 가져온다

avcs 스킬이 작업 흐름을 이렇게 못 박았다: intent → session → lease → operation_propose → validate. 그리고 리뷰는 바깥에서 한다 — "마일스톤마다 avcs sync local 로 push 하고, 웹에서 proposals·이슈· audit 를 리뷰한다."

murmur 가 내부 avcshub 가 된다는 것은 그 리뷰를 여기서 한다는 뜻이다. 대화가 벌어지는 자리와 코드 제안을 보는 자리가 같아야 "사람끼리 일하듯"이 성립한다 — Slack 을 보다가 웹 콘솔을 여는 것은 그 컨셉의 반대다.

왜 이것이 급한가 — 실측된 사고

avcs 스킬에 기록된 것: 2026-08-27, 8개 병렬 세션이 lease 단계를 전부 건너뛴 결과 하루 21 PR · 반복 대형 충돌. 최악은 브랜치 164파일 대 dev 192파일에 32파일이 겹친 것이었고, 같은 기간 lease 객체는 0개였다.

스킬이 남긴 결론이 이 문서의 근거다: "도구는 있었고 아무도 부르지 않았다." 보이지 않는 규율은 지켜지지 않는다. 협업 칸은 그 규율을 화면에 세우는 것이다.

칸

레일의 다섯째 칸 — 협업

「레일」이 네 칸(홈 · DM · 에이전트 · 북마크)을 정했다. 협업은 다섯째 칸이다. 북마크와 나란히 두지 않는 이유: 북마크는 내가 표시한 것이고 협업은 남들이 만들어 내는 것이라, 새 것이 생기면 배지를 받아야 한다.

줄이 말하는 넷

인박스 줄과 같은 규칙이다: 누가(얼굴) · 무슨 제안 (declaredPurpose) · 무엇을 건드리나(effects) · 언제·어느 저장소. 같은 규칙을 쓰는 이유는 두 목록이 같은 종류의 물음 ("내가 무엇을 해야 하나")에 답하기 때문이다.

정렬은 막는 순이다

인박스와 같다. 결정 필요 → 검증 실패 → 검증 대기 → 채택·거부. 시간은 그 안에서만 본다 — 방금 올라온 제안이 어제부터 결정을 기다리는 충돌을 밀어내면 안 된다.

에이전트가 avcs 를 쓰고 있다는 표시는 없다

파일 잠금 목록(lease)을 이 칸에 옮기지 않는다. "누가 어느 파일을 잡았다"는 제안을 읽는 사람이 묻는 질문이 아니다 — 겹침이 실제로 문제가 되면 그것은 결정 필요로 나타나고, 그때 이 칸이 말한다. 도구가 돌고 있다는 사실 자체는 정보가 아니다.

lease 투영은 서버에 그대로 남긴다 — 충돌 판정의 재료이고, 화면에 안 그리는 것과 데이터를 안 받는 것은 다르다.

막는 것

서버가 summary 하나로 눌러 담는다

avcs 객체에는 필요한 것이 다 있다(avcs/src/objects/types.ts 실측):

client.ts 의 toEntries() 가 각 객체를 { logIndex, oid, type, actorKeyId, intentOid, summary } 여섯 칸으로 눌러 담는다. 페치는 이미 전체 객체를 받아 온다 — 버리는 자리가 그 함수 하나다.

상태는 저장되지 않는다 — 파생된다

avcs 주석이 명시한다: "Operation lifecycle status is not stored on the immutable op. It is derived from the presence of evidence/decision objects + policy at materialization time."

일곱 상태다: proposed · validating · accepted · rejected · superseded · needs_decision · quarantined.

그래서 murmur 가 상태를 스스로 계산하면 안 된다. 같은 판정이 두 벌 생기고, 정책이 바뀌면 한 벌만 고쳐져 화면과 avcs 가 다른 말을 한다 — 이 저장소가 projectionState 를 shared 로 뺀 것과 같은 이유다. avcs 가 파생해 준 값을 받아야 한다.

이것이 이 문서의 유일한 미해결 지점이다. avcs-server 의 sync 응답이 파생 상태를 함께 주는지, 아니면 murmur 가 evidence·decision 의 존재로 재구성해야 하는지 — 그 답에 따라 1단계의 크기가 갈린다.

이 문서가 정하지 않는 것

murmur 에서 제안을 만드는 것은 범위 밖이다. 지금 murmur 는 avcs 를 읽기만 한다(fetchSince). 제안·결정을 여기서 만들려면 쓰기 경로가 필요하고, 그것은 avcs-server 쪽 표면 문제다 — 읽는 자리가 먼저 서야 무엇을 쓰고 싶은지 알 수 있다.
