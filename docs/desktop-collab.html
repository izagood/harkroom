murmur 가 hub 자리에 선다

avcs 협업은 원래 웹 hub 에서 리뷰한다. murmur 의 컨셉은 그 자리를 대신하는 것이다 — 대화가 벌어지는 앱에서 제안을 보고 결정한다. 그런데 코드는 반대로 하고 있었다: avcs 객체를 채널 스레드로 투영했다. 그 투영은 걷어냈다(#534) — 아래 「순서」의 0단계가 완료됐고, 이 문서의 나머지는 그 위에 세울 협업 탭의 설계다.

murmur 가 노리는 자리는 세 번째다.

컨셉
원래   avcs ↔ avcs-server ↔ avcshub(웹)
murmur  avcs ↔ avcs-server ↔ murmur 협업 탭

코드 관리·협업은 avcs 를 통해서 한다. murmur 는 그 결과를 보고 결정하는 자리다 — Slack 을 보다가 웹 콘솔을 여는 왕복이 없어지는 것이 이 컨셉의 값이다.

잘못된 것

코드는 avcs 를 스레드로 투영하고 있었다

server/src/avcs/projection.ts 가 avcs 거버넌스 객체를 murmur 채널 메시지로 만들었다. 실측한 매핑 — #534 에서 전부 지웠고, 아래 표는 무엇이 있었는지의 기록이다:

걷어낸 투영#534 · 지웠다
avcs 객체murmur 에서
intent스레드 뿌리가 되고 work_thread 에 매핑됐다
operation그 스레드 아래 답글(배치 병합)
decision·evidence그 스레드 아래 답글
checkpoint·release·finalize채널 메시지
MCP work.linkintent 를 기존 대화 스레드에 묶는 도구 — 이 투영의 배선이었다

왜 이것이 컨셉과 어긋나는가

hub 를 대신한다는 것은 제안을 보는 화면을 갖는 것인데, 투영은 제안을 대화로 바꿔 흘려보낸다. 셋이 어긋난다:

① 스레드는 avcs 의 단위가 아니다. avcs 의 단위는 intent 를 뿌리로 한 제안 트리(intent → operations → evidence + decisions)다. 스레드에 풀어 놓으면 그 구조가 평평한 답글 목록이 된다.

② 지나가 버린다. 제안은 결정될 때까지 머물러야 하는데, 채널 메시지는 스크롤과 함께 지나간다. "지금 무슨 제안이 떠 있나"를 한 자리에서 볼 수 없다.

③ 상태가 없다. 제안에는 상태가 있고(열림·승인됨·머지됨·거부됨) 그것으로 거르고 정렬해야 한다. 메시지에는 그 축이 없다.

사용자 확인(2026-09-07): "스레드 같은게 avcs 에 연동되는 컨셉이 아니였어." 투영은 컨셉을 잘못 구현한 것이므로 걷어냈다(#534). 이미 투영된 system 메시지는 기록이라 남겼고(한 행도 지우지 않았다), lease 투영은 협업 탭이 쓸 재료라 남겼다. 과거 메시지가 채널에 보이는 것은 투영이 아직 돈다는 뜻이 아니다 — 지금 워커가 남기는 것은 active_lease 뿐이다.

모델

제안은 트리다 — avcshub 가 이미 그렇게 조립한다

avcshub 의 groupProposal()(@avcshub/shared)이 객체 배열을 이 모양으로 묶는다:

ProposalViewavcshub/shared/proposal.ts:29
intent — "008 마이그레이션을 되돌린다"
├ operation · declaredPurpose · effects
└ evidence — 검증 결과
└ operation …
decision — approve / reject · 어느 view · 머지된 head

상태는 넷이다: open · approved · merged · rejected. 목록 위의 필터가 그 축을 그대로 쓴다.

murmur 가 이 조립을 다시 짜야 한다. @avcshub/shared 는 비공개 저장소이므로 의존할 수 없다 — 같은 모양을 murmur 안에 세우되, 판정은 avcs 것을 쓴다(아래).

막는 것

파생 상태는 avcs-server 가 주지 않는다

실측으로 세 구간을 다 확인했다.

파생 상태(OperationStatus)는 어디 있나
구간확인
avcs 코어reducer.ts:406 의 reduce() 가 파생한다 — statuses·conflicts·headOps 를 한 번에 낸다
avcs-server준다(0.7.0 · GET /reduced). 이 문서의 앞 판본이 "없다"고 적었고 그것이 맞았다 — 이슈로 제기해 사양(docs/26 §6-4)·설계(docs/27)·참조 구현을 거쳐 들어왔다
avcshub자기 API 계층에서 처리한다(reviewGate.ts)

avcs 주석이 이유를 적었다: "lifecycle status is not stored on the immutable op. It is derived from evidence/decision + policy at materialization time." 상태는 저장되는 값이 아니라 계산되는 값이고, 그 계산은 정책에 달려 있다.

그래서 murmur 는 GET /reduced 를 읽는다

이 문서의 앞 판본은 murmur 서버가 avcs 를 의존해 reduce() 를 직접 부르는 것을 1단계로 적고, avcs-server 에 엔드포인트를 두는 쪽이 더 옳지만 "스펙 변경이 선행이라 그때까지 임시 우회"라고 했다.

그 우회는 필요 없어졌다. 이슈로 제기해 사양·참조 구현·서버까지 들어왔다: avcs 0.50.0(docs/26 §6-4 · 설계 docs/27) → avcs-server 0.7.0(GET /reduced · GET /reduced/blob/:oid · /version 이 reduced·materializer 를 광고).

GET /reduced?view=maindocs/27 §3.1
cursor · materializer · treeHash
statuses — { "operation_ab12…": "accepted", "operation_cd34…": "needs_decision" }
headOps · conflicts · tree

협업 탭이 필요한 것이 **그 응답에 다 있다** — 제안의 상태 · 무엇이 충돌했는지 · 지금 머리가 무엇인지. murmur 서버는 그것을 재료로 실어 주고 화면이 그린다 (#484·#490 과 같은 모양이다).

reduce() 를 직접 조립하지 않는다

murmur 가 상태를 스스로 재구성하면 안 된다. 같은 판정이 두 벌 생기고, 정책이 바뀌면 한 벌만 고쳐져 화면과 avcs 가 다른 말을 한다 — 이 저장소가 projectionState 를 shared 로 뺀 것과 같은 이유다.

앞 판본이 이 대목에서 든 이유 하나가 틀렸다(이슈 리뷰의 지적). "정책이 바뀌면 클라이언트마다 따로 갱신해야 한다"고 적었지만, policy 는 policy ref 로 저장돼 /refs 로 배포되고 리듀서가 "같은 객체 + 같은 정책 + 같은 머티리얼라이저 ⇒ 동일 트리"를 보증한다. 복제본 사이의 어긋남은 sync lag 뿐이고, 그건 서버가 계산해도 응답이 도착할 즈음 똑같이 낡는다. 결론은 그대로다 — 두 번째 구현을 만들지 않는 것이 이유다.

이 응답은 권위가 아니다 — 얇은 클라이언트는 그대로 표시한다

docs/27 §3.6 이 못 박았다: "이 응답은 어느 복제본이든 같은 입력에서 계산할 값이다. 서버는 그중 하나를 계산했을 뿐이다."

복제하는 클라이언트는 자기 환원을 우선하고, 얇은 클라이언트는 이 응답을 그대로 표시한다 — 그것이 이 엔드포인트의 존재 이유다. murmur 협업 탭이 바로 그 얇은 클라이언트다: op 그래프 전량을 들고 있지 않고, 들 이유도 없다.

cursor 와 materializer 를 함께 그리는 이유가 여기 있다 — 화면이 "이 판정이 어느 시점의 것인가"를 말할 수 있어야 sync lag 을 고장으로 읽지 않는다.

탭

협업 탭 — 레일의 다섯째 칸

「레일」이 네 칸(홈 · DM · 에이전트 · 북마크)을 정했다. 협업은 다섯째 칸이고, 이 칸이 avcshub 웹의 /[org]/[repo]/proposals 를 대신한다.

줄이 말하는 넷 — 인박스와 같은 규칙

누가(얼굴) · 무슨 제안(intent.title) · 무엇을 건드리나(effects) · 언제·어느 저장소. 같은 규칙을 쓰는 이유는 두 목록이 같은 물음("내가 무엇을 해야 하나")에 답하기 때문이다.

정렬은 막는 순이다

인박스와 같다: 결정 필요 → 검증 실패 → 열림 → 승인·머지·거부. 시간은 그 안에서만 본다 — 방금 올라온 제안이 어제부터 결정을 기다리는 충돌을 밀어내면 안 된다.

잠금은 그리지 않는다

"누가 어느 파일을 잡았다"(lease)는 제안을 읽는 사람이 묻는 질문이 아니다 — 겹침이 실제로 문제가 되면 결정 필요로 나타나고, 그때 이 탭이 말한다. 도구가 돌고 있다는 사실 자체는 정보가 아니다.

lease 투영은 서버에 남긴다 — 충돌 판정의 재료이고, 화면에 안 그리는 것과 데이터를 안 받는 것은 다르다. 사이드바의 ACTIVE WORK 구역은 사라진다.

왜 급한가

보이지 않는 규율은 지켜지지 않는다

avcs 스킬에 기록된 실측: 2026-08-27, 8개 병렬 세션이 lease 단계를 전부 건너뛴 결과 하루 21 PR · 반복 대형 충돌. 최악은 브랜치 164파일 대 dev 192파일에 32파일이 겹친 것이었고, 같은 기간 lease 객체는 0개였다.

스킬의 결론이 이 문서의 근거다: "도구는 있었고 아무도 부르지 않았다." 협업 탭은 그 규율을 화면에 세우는 것이다 — 웹 콘솔을 따로 열어야 하는 규율은 지켜지지 않는다.

이 문서가 정하지 않는 것

murmur 에서 제안을 만들고 결정하는 것은 범위 밖이다. 지금 murmur 는 avcs 를 읽기만 한다(fetchSince). 쓰기는 서명이 필요하고 (avcs 스킬: "push 는 서명으로만 간다") 그것은 avcs-server 표면 문제다 — 읽는 자리가 먼저 서야 무엇을 쓰고 싶은지 안다.
