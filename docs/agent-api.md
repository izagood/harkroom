# 에이전트 외부 API 호출

에이전트가 외부 HTTP API를 부르는 길은 하나다. 오퍼레이터의 `harkroom-operator api` 래퍼다. 무엇을 부를 수 있는지는 서버 표가
정하고, 키는 래퍼에도 모델에도 보이지 않는다. 머지 래퍼(`docs/agent-merge.md`)와 같은 틀이다.

## 이것은 실수 방지 장치이지 경계가 아니다

이 장치가 막는 것은 두 가지다. 하나는 사람이 허락하지 않은 대상·메서드·경로로 키가 붙어 나가는 것이고, 다른 하나는 키가 채팅·
transcript에 평문으로 도는 것이다. 같은 사용자 계정으로 도는 에이전트는 이 머신의 다른 자격에 닿을 수 있다. 그러므로 악의적인
에이전트를 막는 경계는 아니다.

## 사람이 하는 일

1. 설정 › 나 › 비밀과 API에서 키를 **비밀**로 넣는다.
2. 같은 화면에서 **API 연결**을 만든다. 연결은 이름, 기본 주소(https origin), 인증 방식(Bearer 또는 헤더 이름), 키(내 비밀),
   허용 메서드로 이루어진다.
3. 에이전트 상세의 「할 수 있는 일」에서 그 연결의 `api.call` 권한을 준다. 메서드와 경로 접두를 고르고 만료를 정한다. 쓰기
   메서드가 있으면 만료는 30일 안이어야 한다.

연결의 주소·인증·키를 바꾸면 그 연결로 준 권한이 멈추고, 사람이 다시 줘야 풀린다. 키의 **값**만 바꾸는 것(같은 비밀의 새 판)은
권한을 그대로 둔다.

## 흐름

1. 러너는 멘션 턴을 띄울 때 `GET /agent/api-grants` 를 읽는다. 쓸 수 있는 연결이 하나라도 있으면 claude 에
   `--allowedTools "Bash(<operatorBin> api:*)"` 를 주고, 프롬프트에 연결 이름과 명령 모양을 적는다.
2. 에이전트가 `<operatorBin> api <연결> <METHOD> </경로> [--data @파일|<글자>] [--content-type <형식>]` 를 부른다. 명령은
   하나만 쓴다. `;`·`&&` 로 묶으면 claude 는 조각마다 따로 판정하므로 allow 규칙에 맞지 않는다.
3. 래퍼는 브릿지와 같은 소켓으로 오퍼레이터에 묻는다. 오퍼레이터는 다음 순서로 처리한다.
   - ① 인자를 다시 잰다.
   - ② 턴 임대를 확인한다.
   - ③ 서버 `POST /agent/api-checks` 로 판정을 받는다. 서버는 grant 사슬을 쓰는 순간에 판정하고, 통과하면 키를 오퍼레이터에게만
     건넨다. 이 일은 비밀 접근 기록에 남는다.
   - ④ `new URL(path, baseUrl).origin` 이 연결의 주소와 같은지 다시 확인한다.
   - ⑤ `redirect: 'manual'` 과 60초 시한으로 호출한다.
   - ⑥ `POST /agent/api-results` 로 결과를 알린다. 서버는 그 스레드에 `🔌 <연결> <METHOD> <경로> · <상태> · 권한: <사람> (래퍼 보고)`
     줄을 남긴다.
   - ⑦ 응답 본문에 키 값이 되비치면 가려서 돌려준다.
4. 서버에 닿지 않으면 호출하지 않는다.

## 결정과 한계

- **리다이렉트는 따라가지 않는다.** fetch는 다른 출처로 리다이렉트될 때 `Authorization` 만 떼고 사용자 정의 헤더는 그대로
  보낸다. 그래서 헤더 종류의 키가 남의 호스트로 갈 수 있다. 3xx는 상태와 `location` 만 돌려준다.
- **사설 IP·내부 호스트를 기본 주소로 쓰는 것은 연결 주인의 선택이다.** 래퍼는 이를 막지 않는다. 에이전트가 고를 수 있는 것은
  경로뿐이고 호스트는 사람이 정한다.
- 응답은 2MiB까지 읽고, 모델에게는 앞 256KiB만 준다.
- codex·opencode 등 allow 문법이 없는 하네스에서는 래퍼가 동작하지만 막는 것은 프롬프트뿐이다. 머지와 같은 한계다.
