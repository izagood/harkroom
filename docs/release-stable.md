# Stable 릴리스 절차

데스크톱 앱에는 업데이트 채널이 둘 있다. 이 문서는 **Ludicrous 판 하나를 골라 Stable 로 올리는 절차**다.

| 채널 | 무엇 | 어떻게 나가나 |
|---|---|---|
| Ludicrous | main 머지마다 나오는 최신판 | `release.yml` 이 자동으로 굽고·서명하고·공증해 `releases/latest` 에 둔다 |
| Stable | 시험을 통과한 판 | 사람이 `promote.yml` 을 돌려 그 판의 `latest.json` 만 `stable` 릴리스로 옮긴다(다시 굽지 않는다) |

앱의 기본 채널은 Stable 이다(설정 › 업데이트). 업데이터는 낮은 판으로 내려가지 않는다 — 그래서
**Stable 이 앱보다 낮게 멈추면 그 기기는 업데이트가 멈춘다.** 이 절차가 Stable 을 제때 올리는 장치다.

## 맡는 사람

| 역할 | 맡는 일 |
|---|---|
| QA 담당 | 후보 제안·시험·판정표·관찰 |
| 개발 담당 | ❌ 항목 수정·되돌릴 판(X+1) 준비 |
| 배포 담당 | 운영·스테이징 서버 판올림 |
| 보안·디자인 검토 | 머지·권한 판정 / 화면 판정(시험 중 부를 때) |
| 관리자(maintainer) | 후보 확정·판정 결정·승격 실행·호스트 판 맞추기 |

## 순서

| 단계 | 하는 일 | 누가 | 끝난 표지 |
|---|---|---|---|
| 0 후보 고정 | 그 시점 Ludicrous 최신 **공개** 판을 X 로 정한다. 태그·커밋·서버 이미지 digest 를 적는다 | QA 담당 제안 → 관리자 확정 | 판정 이슈(아래)가 열리고 맨 위에 X·커밋·digest 가 있다 |
| 1 판 맞추기 | 시험 러너 호스트의 앱을 모두 X 로 맞추고 그동안 Ludicrous 업데이트를 끈다. 스테이징 서버도 X 로 | 관리자(호스트) · 배포 담당(스테이징) | 매일 e2e 의 호스트별 판 표가 전부 X |
| 2 시험 | 아래 「시험 목록」대로 | QA 담당 | 판정 이슈에 항목마다 ✅/❌/못 봄 |
| 3 판정 | ❌ 가 있으면 개발 담당이 고치고 고친 판 Y 로 0 단계부터 다시 한다. ❌ 가 없으면 관리자가 판정한다 | QA 담당 보고 → 관리자 결정 | 판정 이슈에 `stable-verdict-pass` 이름표 |
| 4 승격 | ① 운영 서버가 X 이상인지 `/healthz` 로 본다 ② `promote.yml` 을 돌린다 ③ `stable/latest.json` 이 X 이고 Ludicrous `latest` 는 그대로인지 본다 | ① 배포 담당 ② 관리자 ③ QA 담당 | 워크플로 요약 표 |
| 5 관찰 24시간 | Stable 기기의 업데이트 성공·실패 글 수를 본다 | QA 담당 | 판정 이슈에 관찰 결과 한 줄 |
| 6 되돌리기 | 아래 「되돌리기」 | 개발 담당 · 배포 담당, 실행은 관리자 | 고친 판이 Stable |

**서버를 먼저 올린다.** 앱 vX 가 요구하는 서버 하한(`MIN_SERVER_VERSION`, `packages/shared/src/compat.ts`)은
X 이하이므로, 운영 서버가 X 이상이면 Stable 앱은 늘 붙는다. 운영 서버는 Ludicrous 를 따라가고,
서버보다 뒤처진 앱·러너는 서버 쪽 하한으로 막는다(별도 PR).

## 판정 이슈 (승격 관문)

`promote.yml` 은 **판정 이슈가 통과로 표시돼 있지 않으면 멈춘다.**

| 칸 | 값 |
|---|---|
| 자리 | 이 저장소의 GitHub 이슈 하나 |
| 제목 | `Stable 판정 vX` (예: `Stable 판정 v0.5.0`) — 정확히 이 꼴 |
| 이름표 | 통과면 `stable-verdict-pass`. 이름표는 저장소 쓰기 권한이 있는 사람만 붙일 수 있고, 워크플로는 **마지막으로 붙인 사람의 권한**을 다시 확인한다 |
| 본문 | 아래 시험 목록 표에 결과를 채운다. 본문에 `❌` 가 남아 있으면 이름표가 있어도 멈춘다 |

공개 저장소다. 판정 이슈에는 호스트 이름·계정·토큰·스크린샷을 적지 않는다. 그런 근거는 harkroom 스레드에 두고
이슈에는 결과와 메시지 링크 id 만 적는다.

## 시험 목록 (후보 판 X)

| 영역 | 시험 | 자동/손 | 통과 기준 |
|---|---|---|---|
| CI | check · macos-build · launch-smoke · finalize | 자동 | X 가 공개 릴리스이고 `latest.json` 에 서명이 있다 |
| 하네스 격리 | `packages/agent/test/*.real.test.ts` 를 설치된 하네스 판으로 | 손(매일 e2e) | 전부 통과, 하네스 판을 기록 |
| 하네스 매트릭스 | 구독·「API 키 연결」 시험 에이전트 전부에 멘션 → 러너 → 발화. 실패를 기대하는 에이전트는 실패 글 | 손(매일 e2e) | 모두 답하고, 러너 로그의 모델 줄이 설정과 같다. **모든 러너 호스트의 앱이 X** |
| 위임 | A 가 B 에게 `message.delegate` → 결과가 A 의 스레드로 | 손 | 「✅ 만 달고 닫힘」 0건 |

| 카드 | ask · askBundle 에 답하면 그 에이전트가 깬다 | 손 | 답이 그 에이전트의 턴을 띄운다 |

| 서버 ↔ 옛 클라이언트 | 최신 서버 + 앱·러너 X 로 위 흐름 다섯(위임·wake·카드·머지·권한) | 손 | 404 · 스키마 오류 0건 |

## 승격 실행

```sh
gh workflow run promote.yml -R izagood/harkroom -f version=0.5.0
```

워크플로가 차례로 본다: 판 꼴 → 공개 릴리스·`latest.json` → **판정 이슈** → 지금 Stable 보다 낮지 않은지 →
매니페스트가 그 판 자산·서명을 가리키는지. 하나라도 어긋나면 옮기기 전에 선다.

## 되돌리기

- `allow_older=true` 로 매니페스트를 낮은 판으로 돌려도 **이미 X 를 받은 기기는 내려가지 않는다**(업데이터가
  낮은 판을 받지 않는다). 그래서 실제 되돌리기는 **고친 판 X+1 을 바로 승격**하는 것이다.
- X+1 도 판정 이슈가 있어야 승격된다. 급하면 고친 항목과 그 둘레만 시험하고, 줄인 범위를 본문에 적는다.
- 서버는 배포 담당 에서 이전 판으로 돌린다. 단, 2 단계 「서버 되돌리기」가 ✅ 였을 때만 — 마이그레이션은 앞으로만 간다.

## 매일 e2e 가 보는 것

- **Stable 멈춤 경보**: Stable 판이 러너 호스트 대부분의 앱 판보다 낮으면 한 줄 경보를 낸다(앞의 「멈춘 업데이트」를 알아챈다).
- **호스트별 앱 판**: 호스트마다 앱·러너 판을 표로 채운다(1 단계 「판 맞추기」의 근거).
