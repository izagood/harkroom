murmur 설계안 · 2026-09-10

murmur가 허브가 된다

지금은 저장소에 avcshub 링크만 걸 수 있다. 링크를 걸지 않은 경우 murmur가 그 자리에 서서 — 제안을 받고, 화면에서 승인하고, 승인된 것을 GitHub로 내보낸다. 작업이 끝나면 GitHub를 열어 확인하는 대신, murmur 안에 제안이 올라온다.

대상: murmur · avcs · avcs-server 상태: 설계 제안 (코드 변경 없음) 선행: 협업 탭 읽기 자리
1 — 자리

murmur는 avcshub를 보는 것이 아니라 대신한다

지금 murmur는 avcs-server를 읽기만 한다(fetchSince), 그 결과로 남기는 것은 lease 하나다. 제안을 보고 결정하는 일은 avcshub 웹에서, 코드가 실제로 나가는 일은 GitHub에서 일어난다. 사람은 화면을 세 개 연다.

바꾸려는 것은 한 줄이다: avcs-server를 murmur 안에 두고, 승인과 배달을 murmur가 맡는다. 외부 저장소를 쓰는 팀을 위해 지금의 링크 방식(linked)은 그대로 남는다.

2 — 구조

빠진 것은 한 덩어리가 아니라 세 층이다

“murmur가 avcshub를 대체한다”를 기능 하나로 잡으면 첫 릴리스가 나오지 않는다. 쓰기 · 판정 · 배달은 서로 다른 시점에 켤 수 있고, 각각 따로 쓸모가 있다.

층 1 · 쓰기

저장소를 가리키지 않고 갖는다

전역 URL 한 칸(projection_config)을 repo 레코드로 올린다. linked는 지금 그대로 외부 서버를 읽고, hosted는 @izagood/avcs-server를 murmur 안에서 띄운다 — 이미 의존성에 들어 있다. 에이전트의 origin이 murmur가 된다.

층 2 · 판정

승인은 서명이다

승인 버튼을 누르면 데스크탑이 리뷰어 키로 정규 문자열 decision:verdict:view:intent:head에 서명한다. 다른 제안이나 다른 head로 재생할 수 없다. 그 다음은 프로토콜 그대로 POST /integrate.

층 3 · 배달

밖으로 나가는 것은 부작용이다

랜딩된 체크포인트를 저장소에 붙은 배달 대상이 밖으로 내보낸다. GitHub PR · 브랜치 푸시 · 다른 avcs 원격. 배달이 실패해도 승인은 그대로 남고 재시도 큐에만 남는다.

3 — 메커니즘

승인 버튼 한 번에 일어나는 일

판정 다섯 종은 avcs 프로토콜이 이미 정해 놨다

새로 만들 상태 축이 아니다. POST /integrate가 상태 코드로 판정을 나른다.

승인 권한의 정본은 murmur의 role이 아니라 avcs의 view 정책이다. murmur는 그것을 읽어 버튼을 흐리게 할 뿐이다 — 권한을 두 곳에 두면 반드시 갈라진다.

4 — 배달

배달 대상은 저장소에 붙는다

어댑터 셋이 같은 계약을 지킨다: 랜딩된 체크포인트 하나를 받아 바깥에 산출물 하나를 만든다. 멱등키는 (repo, checkpoint, target) — 몇 번을 재시도해도 PR은 하나다.

대상하는 일안전장치
github-pr 체크포인트 트리를 materialize → git plumbing으로 커밋 생성 → 브랜치 push → PR 열기 푸시 전 ls-remote로 기준 tip 확인 · 평범한 refspec(--force 없음)
git-push 같은 경로에서 PR 없이 브랜치로 직행 fast-forward만 · 비-FF는 git이 거절하게 둔다
avcs-remote avcshub나 다른 avcs-server로 objects push + /integrate 프로토콜 그대로 · 판정 5종을 다시 받는다

첫 어댑터는 처음부터 쓰지 않아도 된다. avcshub의 packages/api/src/integration/gitPort.ts에 이 경로가 이미 구현되어 있고, --force류 인자를 금지하는 테스트까지 붙어 있다. 옮겨 오는 편이 다시 짜는 것보다 낫다.

5 — 쓰는 모습

실제로 만들어지면 이렇게 쓴다

스토리 1 · jaebin — 내부 저장소(hosted)

“고쳐 줘” 한 마디에서 PR까지, 화면 하나에서

  1. 채널에서 에이전트를 부른다. “008 마이그레이션을 되돌려 줘”
  2. 에이전트가 intent를 열고 작업한다. push 주소는 GitHub가 아니라 murmur다.
  3. 작업이 끝나면 협업 탭에 제안 한 줄이 선다 — 누가 · 무슨 제안 · 무엇을 건드리나 · 언제.
  4. 제안을 열면 intent → operations → evidence 트리와 검증 결과가 보인다.
  5. jaebin이 승인을 누른다. 데스크탑이 리뷰어 키로 서명한다.
  6. advanced 200 — head가 전진하고 배달 큐가 받는다.
  7. 줄에 칩이 붙는다: PR #124 열림. 링크를 누르면 GitHub로 간다.

스토리 2 · 두 에이전트가 같은 파일을 고쳤다

충돌은 알림이 아니라 결정 필요라는 자리다

  1. alpha와 codex가 각각 messages.ts를 건드린 제안을 올린다.
  2. alpha의 제안이 먼저 승인되어 advanced로 랜딩한다.
  3. codex의 제안을 승인하면 conflict 409 — 수리 패킷이 함께 온다.
  4. 그 줄이 목록 맨 위로 올라오고 인박스 배지가 켜진다. 정렬은 막는 순서다.
  5. 제안을 열면 충돌한 키마다 고를 수 있는 op 두 개와 과거 선례가 나란히 선다.
  6. jaebin이 고르고 이유를 적는다 → decision 객체가 남는다.
  7. 같은 티켓으로 재제출된다. 이번엔 advanced, PR 하나가 나간다.

스토리 3 · 외부 저장소(linked) · 배달 실패

링크를 건 저장소는 지금 그대로, 실패는 승인을 되돌리지 않는다

  1. 회사 avcshub에 이미 있는 저장소는 linked로 둔다. 화면은 똑같다.
  2. 승인하면 murmur가 판정하지 않고 원격 /integrate에 릴레이한다.
  3. 판정도 배달도 원격이 한다. murmur는 그 결과를 같은 줄에 그린다.
  4. hosted 저장소에서 GitHub 토큰이 만료돼 배달이 실패한다.
  5. 승인은 그대로 남는다. 줄에는 배달 실패 · 재시도 3회 칩이 붙는다.
  6. 실패 통지가 스레드로 온다(이미 있는 message.fail 경로).
  7. 토큰을 고치고 다시 배달을 누른다. 멱등키가 같으니 PR은 하나만 생긴다.

6 — 도그푸딩

네 서비스가 다 내 것이라면, murmur는 그 넷의 계측기다

avcs · avcs-server · avcshub · murmur를 한 사람이 만든다면, murmur를 쓰는 모든 순간이 나머지 셋의 테스트다. 그런데 지금 그 테스트 결과가 아무 데도 안 남는다. 증거는 저장소 안에 이미 있다.

서비스실제 버전murmur가 물고 있는 것결과
avcs0.49.4 ^0.45.0 → 0.45.0 설치됨4개 마이너 뒤
avcs-server0.7.0 ^0.3.0 → 0.3.0 설치됨 협업 탭 1단계가 요구하는 GET /reduced가 없는 버전

packages/server/package.json에서 확인한 값이다. 설계 1단계가 “avcs-server 0.7.0 선행”이라고 적혀 있는데 정작 murmur에 깔린 것은 0.3.0 — 도그푸딩이 돌고 있지 않다는 증거가 이미 코드에 있다.

병목은 발견이 아니라 기록이다

오류는 매일 발견된다. 에이전트 턴마다 나온다 — avcs 훅이 느려서 core.hooksPath=/dev/null로 우회하고, 기본 heap으로 OOM이 나서 --max-old-space-size=12288을 붙이고, avcs commit이 트리 전체 드리프트를 잡는다. 셋 다 avcs의 결함 후보인데 어느 저장소에도 없다. 에이전트 메모리와 스레드 스크롤에만 있다. 그러니 만들 것은 “버그를 더 잘 찾는 법”이 아니라 발견을 한 동작으로 저장소에 넣는 길이다.

장치 1

결함은 대상 저장소의 intent다

이슈 트래커를 새로 만들지 않는다. MCP defect.file(repo, …) 하나가 대상 저장소에 intent를 연다. 고치는 operation이 같은 intent 아래로 붙고, 승인·배달은 이미 설계한 길을 그대로 탄다. 별도 축을 만들면 결함과 제안이 영영 안 만난다.

장치 2

증거를 사람이 다시 쓰지 않는다

턴에는 재료가 이미 다 있다 — 실행한 명령, 종료 코드, 스택, 도구 인자. 실패 카드(message.fail)에 [avcs에 결함 열기]를 달고, 누르면 그 재료가 evidence 객체로 따라간다. 재현 절차를 손으로 쓰게 하면 아무도 안 연다.

장치 3

버전 네 쌍이 결함에 박힌다

넷이 동시에 움직이므로 “어느 조합에서 났나”가 결함의 절반이다. GET /version(능력 협상, 프로토콜에 이미 있다)과 릴리스 버전을 자동으로 붙인다. 재현 안 되는 결함의 절반이 여기서 사라진다.

장치 4

어느 저장소인지는 러너가 고른다

MCP 도구 호출 실패 → avcs, /sync·/integrate의 4xx·5xx → avcs-server, 대시보드 → avcshub, 화면·턴 → murmur. 기본값을 러너가 제안하고 사람은 틀렸을 때만 바꾼다.

장치 5

적합성 스위트를 murmur CI가 돈다

hosted 모드가 avcs-server를 내장하는 순간, murmur CI에서 avcs의 npm run conformance를 그 내장 서버에 물릴 수 있다. avcs-server는 “스위트 통과가 곧 지원의 정의”라고 선언해 뒀으니 판정 기준이 이미 있다 — murmur가 avcs-server의 회귀 탐지기가 된다.

장치 6

버전을 고정하지 말고 따라간다

개발 인스턴스는 avcs·avcs-server의 main을 물고, 배포 인스턴스는 고정 버전을 문다. 위 표처럼 4개 마이너가 벌어지면 도그푸딩은 몇 달 전 소프트웨어를 쓰는 일이 되고, 그때 찾는 버그는 이미 고쳐진 버그다.

지표는 하나만 본다

대시보드를 만들지 않는다. 발견된 시각 → 그 고침이 내 손에 도착한 시각, 이 리드타임 하나다. 줄면 루프가 도는 것이고, 늘면 어느 칸이 막혔는지 위 그림에서 짚으면 된다.

자기를 고치는 저장소의 두 가지 조심

  • murmur의 배달은 자동 머지 금지. main 머지가 곧 릴리스라(6~12분) 지금 쓰고 있는 앱이 바뀐다. 되돌릴 수 없는 것은 권한이 있어도 사람 판단으로 남긴다.
  • murmur 저장소는 두 곳에 둔다. hosted로 자기 소스를 담으면, murmur가 죽었을 때 그 소스에 못 간다. 배달 대상이 N개라는 설계가 여기서 값을 한다 — hosted + GitHub 미러를 항상 함께 건다.

8 — 정해졌다 (2026-09-10)

셋 다 사람이 골랐다

서명은 서버 키로 한다

왜 사람 키는 개인키를 쥔 클라이언트에서만 승인이 된다 — 데스크탑은 되지만 모바일·웹 앱에서는 영영 안 된다. 확장을 막는 쪽을 버렸다.
값 잃는 것은 암호학적 귀속 하나다. decision.decidedBy 에 사람을 적고, 감사 기록에 누가 눌렀는지 남기고, 버튼은 로그인 뒤에만 선다 — 신뢰의 뿌리가 개인키에서 murmur 인증으로 옮겨간다.

hosted + 미러 상시

왜 murmur 는 파일 보관소가 아니다. 디스크가 사라져도 파일은 미러에 남고, 잃는 것이 제안 그래프로 한정된다.
범위 미러는 원격지면 무엇이든 되고 여럿이어도 된다(GitHub · avcshub · 다른 avcs-server). 다만 한 방향이다 — 되돌아오는 길을 열면 라인 충돌이 그 경계에서 되살아난다.

값 앱 등록 · private key 보관 · installation 토큰 교환(반나절). 인증은 "토큰 하나 얻기" 함수라 늦어지면 그 함수만 임시로 PAT 를 물릴 수 있다.
근거

이 설계가 딛고 있는 것

  • murmur — packages/server/src/avcs/{client,projection,supervisor}.ts(읽기 전용, lease만 투영), projection_config(041·042), 설정의 ProjectionUrl.tsx. packages/server는 이미 @izagood/avcs·@izagood/avcs-server를 의존성으로 갖고 있다(현재는 테스트에서만 사용).
  • 협업 탭 — docs/desktop-collab.html. 레일 다섯째 칸 · 줄이 말하는 넷 · 막는 순 정렬 · “잠금은 그리지 않는다”. 그 문서가 “murmur에서 제안을 만들고 결정하는 것은 범위 밖”이라고 적어 둔 칸이 이 설계다.
  • avcs 프로토콜 — docs/26-hub-protocol.md §6: POST /finalize(head CAS), POST /integrate(판정 5종, ticketId 멱등), GET /events. integration 객체는 허브만 쓸 수 있다 — 그것이 “허브 자리”의 정의다.
  • avcshub — packages/api/src/integration/gitPort.ts·gitProjection.ts(승인→git 푸시, --force 금지 테스트 포함), packages/shared/src/proposal.ts(decisionMessage, 제안 트리 조립).
설계 제안 · 저장소는 건드리지 않았다. 다음 걸음은 이 내용을 docs/ 문서로 남기고 1단계 스켈레톤을 PR로 내는 것 — 그건 저장소 변경이라 avcs로 진행한다.
