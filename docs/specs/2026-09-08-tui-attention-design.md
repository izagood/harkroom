# TUI 가 사람을 부른다 — 준비 실패는 실패가 아니라 상태 전이다

**날짜**: 2026-09-08
**대체하는 문서**: `2026-09-08-account-readiness-design.md`(계정 카드에 [준비] 버튼을 다는
설계). 그 문서의 재로그인 부분만 §7 로 살아남는다.
**전제**: `2026-09-08-tui-execution-model-design.md`(멘션 턴을 `-p` 대신 TUI 로 돌린다).

## 1. 왜 — 관문은 열거로 끝나지 않는다

TUI 전환이 새 사실을 하나 만들었다: **`claude -p` 는 첫 실행 승인 화면을 건너뛰지만
TUI 는 건너뛰지 않는다.** `-p` 가 설계상 그렇게 동작한다(`claude --help`).

2026-09-08 프로덕션에서 **관문 셋**을 하루에 차례로 만났다. 앞의 것을 지날 때마다
다음 것이 드러났다.

| # | 화면 | 계정 상태 | 실패 모양 |
|---|---|---|---|
| ① | `Choose the text style that looks best with your terminal` | `hasCompletedOnboarding` 없음 | 멈춘다 — **12~30분**을 태우고 무발화로 끝났다 |
| ② | `Is this a project you created or one you trust?` | 워크스페이스가 `projects[dir]` 에 없음 | 멈춘다 |
| ③ | `WARNING: Claude Code running in Bypass Permissions mode` | 수락한 적 없음 | 기본 선택이 **`❯ No, exit`** — **1초**에 `exit 1` |

**③ 은 예외 경로가 아니라 기본 경로다.** `turn.ts:156` 이 murmur 의 `auto` 를 claude 의
`--permission-mode bypassPermissions` 로 번역한다. `auto` 가 에이전트 기본값이므로
**기본 설정의 모든 첫 턴이 이 화면을 만난다.** 그리고 이 화면은 앱이 이미 갖고 있는
개입 UI(터미널 패널 · writer 입력)보다 **앞**에 있다 — 개입할 화면에 닿기 전에 죽는다.

**두 가지가 이 설계를 정한다.**

**첫째, 실패 모양이 서로 다르다.** ①은 30분을 태우고 ③은 1초에 끝난다. 그래서 계정
셋을 준비시키자 증상이 "느린 무발화"에서 "빠른 exit 1"로 **바뀌었다** — 같은 병의 다른
얼굴이었다. 모양으로 분류하는 판정은 관문이 하나 늘 때마다 틀린다.

**둘째, 열거가 끝나지 않는다.** ②는 `workspaceTrust.ts` 가 디스크에 심어 이미 막았다.
그러나 ①과 ③은 못 막았고, 다음 버전이 관문 ④를 더할 수 있다. 하네스의 첫 실행 흐름은
**우리 계약이 아니다.** 부정 목록(이 화면들이 아니면 준비됨)은 구조적으로 진다 —
이미 한 번 졌다(스펙 §5-4: 모달 열거 → 긍정 신호로 교체).

### 지금 코드가 하는 일

`packages/agent/src/pty.ts:498-528` 이 준비 상한(60초)에서 하는 일:

```js
try { proc.kill('SIGKILL'); } catch { /* 이미 죽었으면 회수할 것도 없다 */ }
reject(new PromptNotDeliveredError(Date.now() - startedAt, decodeTailText(tail.snapshot())));
```

**사람이 봐야 할 바로 그 화면을 죽인다.** 승인 화면이 떠 있는 PTY 가 사라지므로, 사람이
열어 볼 대상 자체가 없다. 그리고 `claudeAccounts.ts:140` 이 이 오류를 계정 전환
방아쇠로 읽어 풀을 한 바퀴 돌고, 멘션은 3회를 태운 뒤 "포기하고 읽음 처리한다"로 끝난다.
사람은 **아무것도 못 보고 답만 안 온다.**

### 컨셉이 이미 답을 갖고 있다

murmur 의 TUI 전환은 "터미널에 들어가서 작업하는 것과 동일하게"가 목적이다. 그러면
**사람 손이 필요한 화면에서 할 일은 그 화면을 사람에게 주는 것**이지, 죽이고 재시도하는
것이 아니다. 필요한 조각은 전부 이미 있다:

- 릴레이(러너 → 서버 → 데스크탑 xterm), `TerminalPanel`, `[터미널 열기]`
- 인터랙티브 턴의 무기한 시계(`timeoutMs: 0`)와 고아 회수(viewer 0 → 유예 → SIGTERM)
- 사람 입력 경로(`RelayServerFrame.input`, `AgentSessionView.acceptsInput`)

**개입 UI 는 이미 완성돼 있다.** 사람이 앱 안에서 그 PTY 에 직접 칠 수 있고, 그것이
이 프로젝트의 원래 컨셉이다(#315 운영자 결정: "터미널에 들어가서 작업하는 것과 동일하게").
빠진 것은 그 UI 를 **언제 띄울지 말해 주는 한 마디**뿐이다 — 지금은 사람이 스스로
[터미널 열기]를 눌러야만 닿고, 관문에 걸린 턴은 사람이 그것을 누를 이유조차 모른다.

## 2. 설계

### 2-1. 준비 실패는 PTY 를 죽이지 않는다

`injectPrompt` 의 준비 상한이 하는 일을 바꾼다.

| | 지금 | 바꾼 뒤 |
|---|---|---|
| 60초 안에 준비 신호 없음 | SIGKILL → `PromptNotDeliveredError` → 턴 실패 | PTY **유지**, `onAttention` 콜백 한 번 |
| 그 뒤 | 재시도 3회 → 포기 | 사람을 기다린다(시계 없음 — 멘션 TUI 턴은 이미 `timeoutMs: 0`) |

`PromptNotDeliveredError` 는 **사라지지 않는다.** 사람이 붙을 수 없는 호출자(`prepare`
류의 비대화형 프로브, 테스트)를 위해 `onAttention` 이 없으면 지금 그대로 죽이고 던진다.
즉 **콜백의 유무가 두 정책을 가른다** — 플래그를 따로 두지 않는다.

### 2-2. 사람이 관문을 넘기면 그 자리에서 이어진다

이것이 이 설계의 값 대부분이다. `readyProbe` 는 `proc.onData` 에 걸린 **조건 감시**라
타이머가 죽이지만 않으면 계속 살아 있다:

```
사람이 "Yes, I accept" 선택
  → TUI 가 입력 프롬프트를 그린다
  → readyPattern 이 맞는다
  → 프롬프트가 bracketed paste 로 주입된다
  → 턴이 원래 하려던 일을 한다
```

**사람의 개입이 턴을 대체하지 않고 통과시킨다.** 사람은 관문만 지나면 되고, 답은 여전히
에이전트가 스레드에 쓴다. 새 턴을 띄우지도, 멘션을 다시 집지도 않는다.

이 성질 때문에 "사람이 승인한 뒤 무엇을 해야 하는가"를 UI 가 안내할 필요가 없다.
승인하면 끝이다.

### 2-3. 계정 축을 먼저 태운다 — 사람 부르기는 마지막 수단이다

관문은 **계정마다 따로**다(계정별 `CLAUDE_CONFIG_DIR`). 그래서 풀에 준비된 계정이
하나라도 있으면 **사람 손 없이** 답이 나간다.

순서를 계약으로 못 박는다:

```
계정 1 준비 실패 → (사람 안 부른다) → 계정 2 시도 → … → 풀이 다 막힘 → 그때 사람을 부른다
```

`claudeAccounts.ts:140`(`switchesAccount` 가 `PromptNotDeliveredError` 에 true)은
**그대로 둔다.** 다만 마지막 계정에서까지 준비에 실패했을 때 `withAccountFailover` 가
던지는 그 오류가 사람 부르기로 이어진다.

**트레이드오프**: 사람을 부르기까지 최악 `60초 × 계정 수`가 든다(계정 3개면 3분).
반대로 하면(첫 실패에 바로 부르기) 준비된 계정이 있는데도 사람을 부른다 — 그쪽이 더
나쁘다. **사람의 시간이 기계의 시간보다 비싸다.**

### 2-4. 창은 계정당 하나만 연다

> **확인 완료(2026-09-08).** 관문의 저장 위치를 실물로 갈랐다:
>
> | 관문 | 저장 위치 | 단위 |
> |---|---|---|
> | ① 온보딩 | `<configDir>/.claude.json` 최상위 `hasCompletedOnboarding` | **계정** |
> | ② 폴더 신뢰 | 같은 파일의 `projects[dir].hasTrustDialogAccepted` | **워크스페이스** |
> | ③ bypass 수락 | `<configDir>/settings.json` 의 `skipDangerousModePermissionPrompt` | **계정** |
>
> 재는 법: 키를 지우면 관문이 되살아나고, 되돌리면 사라진다(양방향으로 확인했다).
> ②는 `workspaceTrust.ts` 가 이미 심으므로, **사람을 부르게 되는 관문은 계정 단위뿐이다** —
> 이 절의 전제가 성립한다.
>
> **③은 코드가 심을 수 있다**(§6 이 "범위 밖"으로 밀어 뒀던 것 — 그때는 저장 키를
> 몰랐다). 심는 것이 새 권한을 주지 않는다: `--permission-mode bypassPermissions` 는
> 이미 `turn.ts:156` 에서 murmur 의 `auto` 가 결정한 것이고, 그 화면은 **이미 내려진
> 결정을 계정마다 다시 묻는 확인창**일 뿐이다. 계획의 Task 1.5 가 그것을 심는다.

관문이 계정 단위라면 **한 번 지나면 그 계정의 나머지 턴이 전부 풀린다.** 오늘
7개 스레드가 동시에 걸렸는데, 그대로 열면 창이 7개 뜨고 사람은 같은 승인을 7번 한다.

러너가 **계정별로** 이미 사람을 부른 상태를 기억한다(`Map<accountName, sessionId>`).
같은 계정의 두 번째 턴이 관문에 걸리면 새로 부르지 않고 **먼저 열린 세션 뒤에서
기다린다** — 그 세션이 관문을 지나면 이 턴의 `readyProbe` 도 곧 맞는다(각자의 PTY 는
따로지만, 관문은 디스크의 계정 설정에 기록되므로 **다음 화면 갱신에서 함께 풀린다**).

**정확히는 "함께 풀린다"가 아니라 "각자 풀린다"**: 이미 뜬 PTY 는 자기 화면을 다시
그리지 않을 수 있다. 그래서 §4 의 실물 확인 항목 1번이 이것이다.

### 2-5. 주입이 **먹혔는지**도 재야 한다 — 준비 신호만으로는 부족하다

2026-09-08 실측이 이 절을 만들었다. 프로덕션 턴이 준비 상한 60초가 아니라 **12~30분**을
태우고 무발화로 끝났는데, 그 사이 세션 JSONL 은 만들어지지 않았다 — **프롬프트가 하네스에
닿지 않았다.** 확인한 것과 확인하지 못한 것을 갈라 적는다:

| | |
|---|---|
| 준비 상한이 발화하는가 | **한다.** `timeoutMs: 0` 에서 3015ms 에 `PromptNotDeliveredError` |
| `injectPrompt` 조립이 맞는가 | **맞다.** `mentionTurn.ts:757`, 러너 번들에도 실려 있었다 |
| 관문 화면이 준비로 오판되는가 | **아니다.** 세 화면 모두 `READY = false`(§4-7) |
| 그러면 왜 상한이 안 걸렸는가 | **미확정.** 관측이 남지 않았다 |

**원인을 모른 채로도 이 절은 필요하다.** 확인된 사실 하나로 충분하기 때문이다:
**프롬프트를 넣은 뒤 대화가 시작되지 않는 상태가 30분 동안 실재했고, 아무도 그것을
알아채지 못했다.** 준비 신호는 "화면이 입력을 받을 모양이다"까지만 말하고, 그 뒤에
무슨 일이 있었는지는 말하지 않는다.

원인을 좁히려고 판정을 더 정교하게 만드는 길은 택하지 않는다 — 관문이 늘 때마다 지는
싸움이고, 이 절은 **원인이 무엇이든** 그 상태를 잡는다.

§2-1 은 "준비 신호를 **못 봤을** 때"만 다루므로 이 경로를 통째로 놓친다: 신호를 보고
주입까지 했는데 아무 일도 일어나지 않는 경우다.

그래서 **주입 뒤에 확인 창을 하나 둔다**:

```
프롬프트 주입
  → N초 안에 "대화가 시작됐다"는 증거가 있는가?
      있다 → 정상. 무발화 시계에 맡긴다.
      없다 → 주입이 먹지 않았다 = 사람 필요. §2-1 과 같은 곳으로 간다.
```

**증거로 무엇을 쓰는가.** 세션 JSONL(`<configDir>/projects/*/<sid>.jsonl`)의 존재가
가장 곧다 — 이미 `harnessErrors.ts::readLastApiError` 가 그 경로를 안다. 화면 문자열로
재면(예: "생각 중") 하네스 버전에 묶이지만, 파일 생성은 **대화가 실제로 시작됐다**는
사실 자체다.

**N 의 값**: 주입부터 하네스가 첫 기록을 쓰기까지다. 모델 응답을 기다릴 필요가 없으므로
짧아도 된다(제안: 15초). 이 값이 너무 짧으면 느린 시작을 사람 필요로 오인하고, 너무
길면 오늘처럼 30분을 태운다 — §4 확인 항목 6번이다.

### 2-6. 자원 회수는 새로 만들지 않는다

사람을 기다리는 PTY 는 인터랙티브 턴과 **같은 자원 문제**를 갖는다. 이미 있는 답을
그대로 쓴다(#337): 뷰어 수가 0 이 되면 유예 뒤 SIGTERM. 아무도 안 오면 회수된다.

한 가지만 다르다: 인터랙티브 턴은 **사람이 열어서** 뷰어가 1 부터 시작하지만, 이 턴은
**기계가 불러서** 뷰어가 0 에서 시작한다. 그래서 첫 뷰어가 붙기 전 유예를 따로 둔다
(제안: 10분). 이 값의 의미는 "사람이 자리에 없을 때 얼마나 붙잡고 있을 것인가"다.

## 3. 인터페이스

### 3-1. 러너 → 서버

`RelayRunnerFrame`(`packages/shared/src/index.ts:1735`)에 프레임 하나를 더한다.

```ts
/**
 * 이 세션이 **사람 손을 기다린다**(첫 실행 승인 등). 러너가 준비 신호를 상한 안에
 * 못 봤고, 계정 풀을 다 태운 뒤다 — 즉 이 화면은 다른 계정으로 우회되지 않는다.
 *
 * `interactive.opened` 와 가른 이유는 `interactive.reserved` 를 가른 이유와 같다:
 * "사람이 열었다"와 "기계가 부른다"는 사람이 다음에 할 일이 다르다. 전자는 이미
 * 사람이 앞에 있고, 후자는 **아직 아무도 모른다**.
 */
| { type: 'attention.required'; sessionId: string; accountLabel: string; screen: string }
```

`screen` 은 화면 tail 을 base64 로 실은 것이다 — `output` 과 **같은 규율**로 서버는
열지 않는다. 데스크탑이 터미널을 열기 전에 "무엇을 기다리는지" 한 줄로 보여주는 재료다.

`RunnerCap` 에 `'attention'` 을 더한다. 구 러너는 이 프레임을 안 보내므로, 데스크탑이
없는 기능을 있다고 그리지 않는다.

### 3-2. 서버 → 데스크탑

데스크탑 이벤트 소켓(`packages/desktop/src/state/controller.ts:410` 의 `case` 목록)에
이벤트 하나를 더한다.

```ts
| { type: 'agent.attention'; sessionId: string; channelId: string;
    threadRootId: string | null; agentHandle: string; accountLabel: string }
```

**attach 소켓이 아니라 이벤트 소켓인 이유**: attach 는 이미 붙은 세션에만 온다. 여기서
필요한 것은 **아직 아무도 안 보고 있는 세션**을 알리는 일이다.

### 3-3. 데스크탑 동작

이벤트를 받으면 그 스레드의 터미널 패널을 **자동으로 연다**(`attachAgentSession`).
`api.ts:360` 이 이미 그 경로다.

- 이미 그 스레드의 패널이 열려 있으면 아무것도 안 한다(초점만 준다).
- 앱이 백그라운드면 알림을 띄우고, 사람이 누를 때 연다 — **창을 남의 화면 앞으로
  끌어내지 않는다.**

### 3-4. 러너 쪽 옵션

```ts
injectPrompt?: {
  text: string;
  readyPattern?: RegExp;
  readyTimeoutMs?: number;
  /**
   * 준비 상한을 넘겼을 때 **죽이는 대신** 부른다. 없으면 지금 동작 그대로
   * (SIGKILL + PromptNotDeliveredError) — 사람이 붙을 수 없는 호출자의 경로다.
   */
  onAttention?: (screen: string) => void;
};
```

## 5. 테스트

- **가짜 하네스**(`fake-harness.mjs`)에 관문 모드를 더한다: 승인 화면을 그리고, 특정
  입력을 받으면 입력 프롬프트(`❯` + NBSP)로 넘어간다. 이것이 §2-2 의 회귀선이다.
- `onAttention` 이 **없으면** 지금대로 죽고 던진다는 것을 단언한다 — 두 정책이 콜백
  유무로 갈린다는 계약.
- 계정 축을 다 태운 **뒤에야** 부른다는 것을 `withAccountFailover` 조합으로 단언한다
  (§2-3). 이 줄이 없으면 준비된 계정이 있는데도 사람을 부르는 회귀가 조용히 들어온다.
- 같은 계정의 두 번째 턴이 **부르지 않는다**는 것(§2-4).
- 관문 화면 픽스처 3종(①②③)에 대해 `looksReadyForPrompt` 가 거짓임을 단언한다.
  오늘 실측한 화면을 그대로 뜬다.

## 7. 흡수되지 않고 남는 것 — [다시 로그인]

앞 문서(`account-readiness-design.md`)의 세 상태 중 **로그인 필요**는 이 설계로
해결되지 않는다. 만료된 세션은 TUI 를 열어도 사람이 브라우저로 로그인해야 하고,
그 흐름은 앱에 **이미 있다**(`daemon/claudeAccounts.ts` 의 `loginStart(pool, account)`).

문제는 구현이 아니라 **버튼의 자리**였다: 계정 카드가 주는 유일한 행동이
`Remove account` 인데, 그것은 세션 파일과 신뢰 기록까지 함께 버린다. 사람이 원한 것은
다시 로그인하는 것뿐인데 화면이 "지우고 다시 만들어라"만 제안하고 있었다.

`loginStart` 는 이미 계정 이름을 받는다. **계정 카드에 [다시 로그인] 을 두는 것**이
전부다. 이 설계와 독립이므로 따로 낸다.
