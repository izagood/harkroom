# 계정이 "지금 쓸 수 있는가" — 앱이 상태를 말하고 행동을 준다

2026-09-08. 대상: `packages/daemon`(계정 포트)·`packages/desktop`(설정 화면·Tauri 명령). 서버·러너는 바뀌지 않는다.

## 1. 왜 — 계정 카드가 말할 수 없는 상태가 둘 있다

계정 설정 화면은 `status.loggedIn` 하나로 상태를 그리고, 계정마다 주는 행동은
`Remove account` 하나뿐이다. 로그인 시작은 **새 계정 추가 폼에만** 있다. 그 결과 두 상황에서
사람이 할 수 있는 것이 없다.

### ① 만료 — 반드시 일어나고, 오늘 일어났다

2026-09-08 러너 로그: `Failed to authenticate: OAuth session expired and could not be
refreshed` 가 14건. 그 계정의 카드에는 `Not signed in` 이 경고색으로 뜨지만 **되살릴 버튼이
없다.** 화면이 주는 유일한 행동은 `Remove account` 이고, 그것은 그 계정의 세션 파일과
워크스페이스 신뢰 기록까지 함께 버린다 — 사람이 원한 것은 다시 로그인하는 것뿐이다.

### ② 첫 실행 승인 — TUI 전환이 새로 만든 상태

멘션 턴이 TUI 로 돌기 시작하면서(`2026-09-08-tui-execution-model-design.md`) 하네스가 첫
실행 승인을 묻는다. `-p` 는 이것을 **설계상 건너뛴다**(claude `--help`: *"The workspace trust
dialog is skipped when Claude is run in non-interactive mode"*). 실물에서 셋을 만났다:

| 승인 화면 | 언제 |
|---|---|
| 온보딩 — `Select login method:` | config 디렉터리에 `hasCompletedOnboarding` 이 없을 때 |
| 팀 텔레메트리 — `Yes, I trust these settings` | 팀 admin 이 모니터링을 켜 조직 설정이 그 계정에 동기화됐을 때 |
| 폴더 신뢰 — `Yes, I trust this folder` | 처음 보는 작업 디렉터리 |

셋 중 앞의 둘은 **계정 수준**이라 사람이 한 번 답해야 한다(스레드 워크스페이스 신뢰만
러너가 적는다 — `workspaceTrust.ts`).

**그런데 그 상태를 앱이 볼 수 없다.** 실측: `claude auth status --json` 의 출력이 준비된
계정과 안 된 계정에서 **완전히 동일하다**(`loggedIn: true` 포함 아홉 필드가 같다). 그래서
"로그인은 됐는데 아직 못 쓴다"를 상태 API 로는 표현할 방법이 없다.

지금 그 상태의 결과는 이렇다: 그 계정으로 도는 모든 턴이 준비 신호를 못 봐 상한에서
실패하고, 사람은 스레드에서 `(답변에 실패했습니다 — 운영자 확인이 필요합니다)` 만 본다.
**무엇을 확인해야 하는지는 어디에도 없다.**

## 2. 설계 — 상태 셋, 행동 둘

계정 카드가 *"이 계정이 지금 쓸 수 있는가"* 를 말하고 그에 맞는 행동을 준다.

| 상태 | 판정 | 카드가 주는 행동 |
|---|---|---|
| **쓸 수 있음** | `loggedIn` 이고 TUI 가 준비 상태에 닿는다 | 없음 |
| **승인 필요** | `loggedIn` 인데 TUI 가 준비에 못 닿는다 | **[준비]** — 앱 안 터미널로 승인 화면을 보여 준다 |
| **로그인 필요** | `loggedIn: false` | **[다시 로그인]** — 기존 로그인 흐름 재사용 |

**판정 순서가 계약이다.** `loggedIn` 을 **먼저** 본다. 미로그인 계정으로 TUI 를 띄우면
로그인 화면이 뜰 뿐인데, 그것이 "준비에 못 닿았다" 로 읽혀 `승인 필요` 로 잘못 분류된다.
그러면 사람은 [준비] 를 눌렀다가 로그인 화면을 만나고, 그 화면이 무엇을 하는 자리인지 알 수
없다. 두 상태는 사람이 할 일이 다르므로 화면에서도 갈려야 한다.

### 2-1. [다시 로그인] — 자리를 옮기는 일이다

`loginStart(pool, account)` 는 **이미 계정 이름을 받는다.** 새 계정 추가 폼에만 있던 그
버튼을 계정 카드로 끌어오면 만료 복구가 성립한다. 새 구현이 아니라 배치의 문제였다.

`claude auth login --claudeai` 는 그 config 디렉터리에 다시 로그인하므로 세션 파일·신뢰
기록·프로젝트 상태가 그대로 남는다 — `Remove account` 후 재등록과 다른 점이 이것이다.

### 2-2. [준비] — 로그인이 쓰는 **모양**을 그대로 따른다

새 전송 방식을 만들지 않는다. 로그인은 이미 "daemon 이 자식을 띄우고, 이벤트를 앱으로
흘리고, 앱이 입력을 되돌려 보낸다"로 돌고 있고(`onLoginEvent` + `loginSubmit`), 승인 통과는
그 왕복이 나르는 것만 다르다 — "URL 하나와 코드 하나" 대신 "화면과 키".

**타입은 형제로 둔다**(§3). 한 이벤트에 `url`·`code`·`screen` 을 다 넣으면 어느 조합이
유효한지 타입이 말하지 못하고, 화면을 그리는 쪽이 매번 분기를 다시 조립한다. 모양은 같고
실어 나르는 것이 다르면 타입도 갈리는 것이 맞다.

```
daemon                                  앱
  claude(TUI) ──PTY──▶ 화면 바이트  ──▶  xterm 이 그린다
                       키 바이트    ◀──  사람이 친다
  looksReadyForPrompt(화면) === true
                       done        ──▶  창을 닫고 "쓸 수 있음"
```

**끝 판정은 `looksReadyForPrompt` 다 — 러너가 쓰는 그 함수 그대로.** 앱이 자기 판정을 새로
만들면 "준비됐다"의 정의가 앱과 러너 사이에서 갈리고, 그러면 앱은 초록인데 턴은 실패한다.
2026-09-08 사고의 뿌리가 정확히 그 종류(코드의 정의와 실물이 갈림)였으므로 같은 모양을
한 번 더 만들지 않는다.

**상한을 둔다(90초).** 사람이 창을 열어 두고 잊으면 PTY 가 남는다. 러너의 회수 규율과 같고,
`shutdownLogins()` 가 이미 진행 중인 로그인을 회수하듯 준비 세션도 같은 자리에서 회수한다.

### 2-3. 상태 판정 — `ready` 를 재는 값

`ClaudeAuthStatus` 에 `ready?: boolean` 을 더한다. `auth status --json` 이 이 사실을 모르므로
(§1 실측) **실제로 TUI 를 잠깐 띄워** 잰다: PTY 로 열고, `looksReadyForPrompt` 가 참이 되면
`ready: true`, 상한(10초) 안에 못 보면 `false`, 그리고 어느 쪽이든 죽인다.

**`list()` 마다 계정 수만큼 프로세스를 띄우면 안 된다.** 설정 화면을 열 때마다 그 비용을
내는 것은 과하다. 그래서:

- `list()` 는 `ready` 를 **디스크에서 싸게 추정한다**: `<configDir>/.claude.json` 의
  `hasCompletedOnboarding` 이 참인가. 이것은 저장소가 이미 세운 "디스크의 사실 관측" 규율과
  같은 자리다(`claudeSessions.ts`·`codexSessions.ts`·`claudeAccounts.ts` 의 *"목록의 진실은
  디스크다"*).
- **추정은 완전하지 않다** — 팀 텔레메트리 승인처럼 다른 곳에 기록되는 것을 놓친다. 그래서
  이 값은 "확실히 준비 안 됨"만 신뢰하고, 참일 때는 "아마 됨"이다. 놓친 경우의 안전망은
  러너 쪽에 이미 있다: 준비 상한 60초에서 빠르게 실패하고 계정 축이 다음으로 넘어간다.
- 정확한 판정이 필요한 자리는 [준비] 세션의 **끝**이다. 거기서는 실물 TUI 가 이미 떠 있으므로
  `looksReadyForPrompt` 로 확정한다.

이 비대칭이 의도다: **화면은 싸게 추정하고, 준비를 마쳤다는 선언은 실물로 확정한다.**

## 3. 인터페이스

`ClaudeAccountsPort` 에 셋을 더한다. 이름을 `login*` 과 나란히 둔다 — 같은 채널을 쓴다는
사실이 이름에서 보여야 한다.

```ts
  /** 승인 통과 세션을 연다. 그 계정 디렉터리로 TUI 를 PTY 에 띄운다. */
  prepareStart(pool: string, account: string): Promise<{ sessionId: string }>;
  /** 사람이 친 바이트를 그 PTY 로 보낸다. base64 — 제어 문자가 그대로 가야 한다. */
  prepareInput(sessionId: string, dataBase64: string): Promise<void>;
  /** 사람이 창을 닫았다. 상한 전에도 회수한다. */
  prepareCancel(sessionId: string): Promise<void>;
```

이벤트는 기존 `ClaudeLoginEvent` 를 넓히지 않고 **형제 타입**을 둔다 — 필드가 겹치지 않고,
한 타입에 `url`·`code`·`screen` 을 다 넣으면 어느 조합이 유효한지 타입이 말하지 못한다.

```ts
export interface ClaudePrepareEvent {
  sessionId: string;
  /** PTY 가 뱉은 raw 바이트(base64). xterm 까지 **한 번도 디코드되지 않고** 간다. */
  screenBase64?: string;
  /** 끝났다. `ready` 가 그 결과다. */
  done?: boolean;
  ready?: boolean;
  /** 사람이 읽는 실패 사유. `done` 과 함께 온다. */
  error?: string;
}
```

**base64 인 이유**는 릴레이가 이미 세운 규율과 같다(`shared` 의 릴레이 절): 청크 경계에서
잘린 UTF-8 을 문자열로 뜨면 U+FFFD 로 치환돼 되돌릴 수 없고, ANSI 이스케이프가 조각나
화면이 깨진다.

Tauri 명령 셋(`claude_account_prepare_start`·`_input`·`_cancel`)과 이벤트
(`murmur://claude-prepare`)를 기존 로그인 명령 옆에 나란히 둔다.

## 4. daemon 이 node-pty 를 물게 된다

`claudeAccounts.ts` 의 `nodeSpawnLogin` 주석이 이것을 **명시적으로 거절했다**:

> **PTY 가 아니라 파이프다.** 실측(claude 2.1.263): 파이프에서도 URL 을 찍고 stdin 에서
> 코드를 읽는다. PTY 를 쓰면 데몬이 node-pty 를 물게 되고 얻는 것이 없다.

그 판단은 **로그인에 대해 여전히 옳다** — 로그인은 파이프로 되므로 바꾸지 않는다. 바뀐 것은
승인 통과라는 새 요구다: 승인 화면은 TUI 이고 TUI 는 tty 를 요구한다. 즉 "얻는 것이 없다"가
더는 참이 아니다. 그 주석에 이 근거를 덧붙이고 파이프 경로는 그대로 둔다.

**러너의 릴레이를 재사용하지 않는 이유**는 순환이다. 러너는 이미 node-pty 와 릴레이를 갖고
있지만, **준비가 안 돼서 러너가 실패하는 상황에서 그 러너로 준비를 하라는 것**이 된다.
러너가 안 떠 있으면 준비할 길이 없다. 계정은 에이전트에 매이지 않는 로컬 자산이므로 계정을
관리하는 daemon 이 그 자리다.

## 5. 테스트

| 대상 | 검사 |
|---|---|
| 상태 분류 | `loggedIn: false` → `로그인 필요`(준비를 재지 않는다) / `loggedIn` + `hasCompletedOnboarding` 없음 → `승인 필요` / 둘 다 → `쓸 수 있음` |
| 판정 순서 | 미로그인 계정에 [준비] 를 주지 않는다 — 로그인 화면을 승인 화면으로 오인하지 않는다 |
| 준비 세션 | 화면 바이트가 base64 로 그대로 흐른다 / 입력이 PTY 로 간다 / `looksReadyForPrompt` 가 참이면 `done+ready` 로 끝난다 |
| 상한 | 90초를 넘기면 회수하고 `done+ready:false` 를 낸다 |
| 회수 | `prepareCancel` 과 데몬 종료가 PTY 를 남기지 않는다 |
| 재로그인 | 계정 카드의 [다시 로그인] 이 그 계정 이름으로 `loginStart` 를 부른다(새 계정 폼과 같은 흐름) |

`looksReadyForPrompt` 는 러너의 것을 그대로 쓴다 — 사본을 만들면 두 판정이 갈린다.
`@murmur/agent` 를 daemon 이 의존하지 않으므로 그 함수를 `@murmur/shared` 로 옮긴다.

## 6. 범위 밖

- **승인을 앱이 대신 누르기.** 팀 텔레메트리 승인은 *"조직이 이 기계의 텔레메트리를 수집하는
  것을 인정하는가"* 이고, 그것은 사람이 답할 질문이다. 앱은 화면을 **보여 줄** 뿐 대신 답하지
  않는다.
- **일반 터미널.** [준비] 세션은 준비 전용이고 준비되면 닫힌다. 그 계정으로 대화까지 하게
  하면 끝을 정할 수 없고(사람이 닫을 때까지 산다) 준비 여부를 언제 판정할지가 모호해진다.
- **codex 계정.** codex 는 `CODEX_HOME` 축이 따로이고 앱에 그 화면이 아직 없다. 같은 모양이
  필요해지면 이 설계를 따른다.
- **자동 재로그인.** 만료를 감지해 앱이 스스로 로그인 창을 띄우지 않는다 — OAuth 는 브라우저와
  사람을 요구하고, 사람이 안 보는 사이에 브라우저가 뜨는 것은 놀라운 일이다. 카드가 상태를
  말하고 사람이 누른다.
