# 러너 실행 모델 교체 — 멘션 턴을 TUI 로 돌린다

2026-09-08. 대상: `packages/agent`. **동작을 여는 데는 서버·데스크탑을 안 바꾼다**(§2).
철거(3-6, P4)에서만 죽은 표면을 걷어낸다 — 그것은 기능 추가가 아니라 정리다.

`2026-09-01-runner-sessions-pty-design.md` §5-3("멘션 턴은 관찰 전용이다")을 뒤집는다.
그 결정을 뒤집을 수 있게 만든 실측은 같은 문서 §5-4 에 있다.

## 1. 왜 — 우회 구조물이 원인을 대신하고 있다

사람이 진행 중인 멘션 턴에 **칠 수 없다.** 원인은 하나다: 프롬프트를 파일로 넘기느라
(`#117`, argv 의 `ps` 노출 회피) `composeSpawn` 이 `sh -c 'exec claude … < 파일'` 로 감싸고,
그래서 자식의 fd 0 이 PTY 가 아니라 일반 파일이다 → `acceptsPtyInput` 거짓 → 서버가 writer
차례를 안 준다(§5-3).

그 제약 위에 우회 구조물이 쌓였다:

- `[이어받기]` — 예약해 두고 그 턴이 **끝나기를 기다렸다가** 새 PTY 를 띄운다.
- `reserveHandoff`·`clearHandoff`·`resumeHandoff`·`turnRegistry.handoffs`
- `WriterDeniedReason` 의 `'observe-only'` 와 그 화면 문구

넷 다 *"`-p` 라서 못 친다"* 를 사람에게 설명하거나 우회하려고 존재한다. **원인을 없애면 넷이
함께 사라진다.**

그리고 이것이 제품 컨셉과 어긋나 있던 자리다. 터미널을 보여 주는 이유는 사람이 **개입**할 수
있게 하려는 것인데, 지금은 볼 수만 있다.

## 2. 왜 동작을 여는 데 서버·데스크탑이 안 바뀌는가

§5-3 이 세운 판정이 옳았기 때문이다:

> 판정은 하네스 종류(`claude -p` 인지)가 아니라 fd 0 의 정체 하나로 한다 — 원인이 하네스가
> 아니므로, 하네스가 늘어도 이 판정은 안 깨진다.

입력 배선(릴레이, attach 소켓, xterm `onInput`)은 이미 전부 있고, 차례 판정은 러너가 announce
에 싣는 `acceptsInput` **한 값**에서 파생된다. 러너가 `stdinFile: null` 로 띄우는 순간 그 값이
참이 되고, 서버·데스크탑은 손댈 것이 없다. **P1~P3 은 러너 안에서 끝난다.**

P4(철거)만 예외다. 그때 지우는 것(`[이어받기]` 버튼, `handoff` 요청 필드)은 새 동작을 위한
변경이 아니라 **P3 이 끝나면 아무도 안 부르게 되는 표면**을 걷어내는 일이다. 그래서 순서가
계약이다 — 먼저 지우면 이어받기가 필요한 구간이 남는다.

**인터럽트에도 새 표면이 필요 없다.** 데스크탑 xterm 의 `Ctrl+C` 가 릴레이를 타고 그대로
PTY 에 닿고, 그 뒤는 하네스가 한다(§5-4 실측: 화면에 `Interrupted · What should Claude do
instead?` 가 뜨고 프로세스는 살아 있다). 리액션 제스처·서버 판정·릴레이 프레임·레지스트리의
kill 손잡이를 **하나도 만들지 않는다.**

## 3. 설계

### 3-1. TUI 조립

`turn.ts::CLAUDE_PRESET.session()` 의 `mode` 분기를 없앤다.

```
전: mention     → ['-p','--session-id',id] / ['-p','-r',id]
    interactive →      ['--session-id',id] /      ['-r',id]
후: 둘 다             ['--session-id',id] /      ['-r',id]
```

`mentionTurn.ts` 는 `writePromptFile` 호출을 멈추고 `stdinFile: null` 을 넘긴다. 프롬프트는
`runPtyTurn` 의 새 옵션(`injectPrompt`)으로 가서 **bracketed paste**(`ESC[200~ … ESC[201~`)로
감싸 주입되고 `\r` 로 전송된다. 감싸지 않으면 여러 줄 프롬프트의 첫 개행에서 조기 전송된다.

**지시문은 그대로 파일이다**(`--append-system-prompt-file`). 바뀌는 것은 대화 본문의 경로뿐이고,
`#92`·`#117` 이 막은 것(`ps` 노출)은 주입 경로에서도 그대로 막혀 있다 — argv 를 지나지 않는다.

**부팅 대기는 조건 기반이어야 한다.** TUI 는 뜨는 데 수 초가 걸리고, 준비 전에 쓴 바이트는
사라진다. 고정 슬립은 두 방향으로 틀린다(짧으면 프롬프트를 잃고, 길면 매 턴을 그만큼 늦춘다).
PTY 출력에서 입력 프롬프트 표시가 나타날 때까지 기다리고 **상한을 둔다**; 상한을 넘기면 그
턴은 실패로 끝난다(조용히 프롬프트 없는 TUI 를 남기지 않는다).

### 3-2. 턴의 끝 — 발화 + 관찰자 없음

TUI 는 답하고도 죽지 않는다. 그래서 "프로세스 종료 = 턴의 끝"이 성립하지 않는다.
**이 설계의 유일한 실질 결정이 여기다.**

- **발화 감지**: 주기적으로 `readThread(channelId, anchor, turnStartSeq)` 를 읽어
  `countOwnPostsSince > 0` 이면 그 턴은 답을 냈다. (`kind='progress'` 는 이미 제외된다.)
- **회수**: 발화하면 회수를 예약하되, **관찰자가 있으면 유예한다**. viewer 0 이 되면
  `interactiveOrphanMs` 뒤 SIGTERM → 유예 → SIGKILL.

회수 장치를 새로 만들지 않는다 — `interactiveTurn.ts` 의 `onViewerCount` 경로가 이미
그것이고, 그 주석이 근거를 적어 뒀다: *"viewer 0 이 유예를 시작하고, 0 이 아닌 count 가
취소한다. 패널 닫힘·소켓 단절·앱 강제종료가 서버 관점에서 전부 '뷰어 소멸' 하나로 수렴한다."*

**"프로세스 = 턴" 불변식은 사실상 유지된다.** 끝의 정의가 "프로세스가 죽었다"에서 "답했고
아무도 안 본다"로 넓어질 뿐, 프로세스가 턴보다 오래 살아남아 다음 턴을 처리하지는 않는다.
다음 멘션은 지금과 같이 새 프로세스이고, `-r` 이 맥락을 잇는다(§5-4 에서 TUI resume 확인).

**스레드 상주 PTY 는 채택하지 않았다.** 사람이 답을 보고 바로 이어 치는 값은 위 유예가 거의
다 준다. 반면 상주는 활성 스레드 수만큼 프로세스가 **영구히** 산다 — 실측 RSS 182~285MB
(2026-09-08, 동시 7턴 피크 2.0GB)이므로 스레드 수십 개면 수 GB 가 상시 점유된다. 축출 정책이
새로 필요하고, `turnTimeoutMs`·고아 회수·레지스트리 이원화를 전부 다시 정해야 한다. 얻는 것
(사람이 안 보는 동안에도 프로세스를 살려 두는 것)에 그만한 값이 없다.

### 3-3. 타임아웃 — 재는 대상이 바뀐다

`turnTimeoutMs` 는 남되 **무발화 경과**를 잰다(프로세스 수명이 아니다). 초과하면 현행과 같이
SIGTERM → 유예 → SIGKILL 이고, 그 턴은 실패로 처리된다.

**관찰자가 있으면 타임아웃도 유예한다.** 인터랙티브 턴이 이미 `timeoutMs: 0`(무기한)인 것과
같은 규칙이다. 회수(3-2)·유예(3-5)와 함께 한 문장으로 모인다: **사람이 보고 있으면 러너는
끼어들지 않는다.**

### 3-4. 실패 판정 — tail 을 버린다

지금 실패 분류는 하네스의 종료 tail 문자열에 걸려 있다. TUI 는 턴마다 종료하지 않아 exit code
가 없고, 주입한 프롬프트가 PTY 에 에코돼 tail 에 섞인다(§5-4 실측). 그대로 두면 **에이전트를
멘션할 수 있는 사람이 본문에 `authentication_error` 같은 문구를 넣는 것만으로 그 러너를 78 로
물러나게 할 수 있다** — 그 러너가 맡은 모든 스레드가 함께 죽는다.

| 실패 | 지금 | 바뀜 |
|---|---|---|
| murmur PAT | HTTP status 401/403 | **그대로** (`policy.ts` 가 이미 구조적으로 잰다) |
| 사용량 한도 | tail 문구 | 세션 JSONL 의 `isApiErrorMessage` 레코드 |
| 하네스 미로그인 | tail 문구 | **턴 시작 전 프리플라이트** |
| 세션 id 충돌 | tail 문구 | 프로세스 즉사 → exit code |

**세션 JSONL 이 더 나은 출처라는 것은 이미 관측돼 있었다.** `main.ts` 의 한도 분기 주석:

> 2026-09-07 19:03 사건에서 이 줄은 "풀림: 알 수 없음"만 남겼고, 그래서 CLI 가 낸 문구
> (세션 파일에는 `resets 10:50pm (Asia/Seoul)` 이 있었다)와 판정 사이의 어디가 어긋났는지
> 알 수 없었다.

tail 은 끝 2KB 링이라 시각이 잘렸는데 세션 파일에는 온전히 있었다. 실측(2026-09-08, 로컬
세션 전수 조사): `isApiErrorMessage: true` 인 `assistant` 레코드가 79건 있고, 내용이 정확히
`You've hit your session limit · resets 10:50pm (Asia/Seoul)` 이다. 즉 **명시적 플래그**가
붙고, 그 문자열은 **하네스 자신의 것**이라 사용자 프롬프트가 섞일 수 없다.

이 이설은 이 저장소가 이미 세운 원칙과 같은 자리에 선다 — `claudeSessions.ts`:
*"하네스 **출력**을 파싱하는 것이 아니다 … 디스크의 사실 관측이고, 러너의 파싱 금지 원칙에
어긋나지 않는다."* `codexSessions.ts` 의 rollout 발견이 같은 패턴의 두 번째 사례다.

**미로그인을 사후 판정으로 두면 안 된다.** TUI 는 미로그인이면 로그인 화면을 띄우고 앉아
있는다 — 발화가 없으니 무발화 타임아웃(기본 30분)까지 기다리게 된다. 턴을 띄우기 **전에**
확인한다. `claudeAccounts.ts` 가 이미 계정 디렉터리와 자격증명 위치(경로 sha256 앞 8자로
파생되는 keychain 서비스명, `.credentials.json` 폴백)를 알고 있고, 그 파일의 원칙이
*"목록의 진실은 디스크다"* 이므로 같은 자리에 하나를 더 얹는다.

### 3-5. 유예 규칙이 바뀐다 — `kind` 가 아니라 `viewer`

사람이 터미널에서 타이핑하는 중에 러너가 프롬프트를 주입하면 두 입력이 같은 PTY 에서 섞인다.
그래서 `MentionQueue` 와 유예는 **사라지지 않는다.** 판정 기준만 바뀐다:

```
전: registry.controlOf(threadKey)   — 그 스레드의 턴이 'interactive' 종류인가
후: 그 스레드의 세션에 viewer 가 있는가
```

멘션 턴이 TUI 가 되면 두 종류의 실질 차이가 "누가 열었나"뿐이므로, 종류로 재는 것이 더는
뜻을 갖지 않는다. 3-2·3-3 과 같은 조건 하나로 수렴한다.

### 3-6. 철거

- `[이어받기]` UI(`TerminalPanel.tsx`)와 그 상태(`waiting`·거절 문구)
- `interactiveTurn.ts` 의 handoff 3분기와 `resumeHandoff`
- `turnRegistry.ts` 의 `handoffs`·`reserveHandoff`·`clearHandoff`·`handoff`
- `mentionScheduler.ts` 의 `hooks.resumeHandoff`

**남는 것**: `WriterDeniedReason` 의 `'observe-only'` — P5 전까지 codex 는 `exec`(stdinFile)로
돌고 그 세션은 관찰 전용이다. 사유를 지우면 그 화면이 원인을 지어낸다. P5 가 끝나면 그때
지운다.

### 3-7. 마이그레이션 — 코드가 없다

`-p` 로 만든 세션을 TUI `-r` 이 그대로 이어받는다(§5-4 실측: 앞 턴의 사실 유지,
`No conversation found` 없음). 기존 스레드는 **다음 턴이 TUI 로 뜨면서 자동 전환**되고
`sessions.json` 레코드도 그대로 유효하다. 변환 코드도, 일회성 스크립트도 필요 없다.

## 4. 테스트

| 대상 | 검사 |
|---|---|
| `turn.ts` | 멘션 모드가 `-p` 를 안 붙인다. `acceptance-cli.test.ts` 가 조립한 argv 를 실물 CLI 에 대조하므로 그 케이스를 갱신한다 |
| `pty.ts` | 주입이 bracketed paste 로 감싸진다 / 부팅 대기가 조건 기반이고 상한이 있다 / 상한 초과가 실패로 끝난다 |
| 턴의 끝 | 발화하면 회수를 예약한다 / viewer > 0 이면 유예한다 / viewer 0 이 되면 유예 뒤 회수한다 |
| 타임아웃 | 무발화 경과로 잰다 / 관찰자가 있으면 안 잰다 |
| `policy.ts` | JSONL fixture 로 한도·에러를 판정한다. 기존 tail 테스트는 삭제가 아니라 **이설**이다 |
| 프리플라이트 | 미로그인 계정이면 턴을 띄우지 않고 계정 축이 다음으로 넘어간다 |
| 유예 | viewer 가 있는 스레드의 멘션은 주입하지 않는다 (`mentionScheduler` 회귀선) |

## 5. 페이즈

| | 내용 | 선행 |
|---|---|---|
| **P1** | 3-4 실패 판정 이설 (JSONL + 프리플라이트) | 없음 — **단독 출하 가능** |
| P2 | 3-1 TUI 조립 + 프롬프트 주입 | P1 |
| P3 | 3-2·3-3 턴의 끝과 타임아웃, 3-5 유예 규칙 | P2 |
| P4 | 3-6 철거 | P3 |
| P5 | codex 를 같은 모델로 (신뢰 대화상자 처리 포함) | P4 |

**P1 을 먼저 독립적으로 출하한다.** TUI 전환과 무관하게 지금 있는 버그(2026-09-07 의 "풀림:
알 수 없음")를 고치고, 실패 판정이 안정된 뒤에 실행 모델을 바꾸는 편이 안전하다 — 두 변경이
겹치면 실패가 났을 때 어느 쪽 탓인지 가릴 수 없다.

## 6. 범위 밖

- **codex 를 P5 로 미룬다(범위 밖이 아니다).** 2026-09-08 실측에서 codex 도 claude 와 같은
  성질을 보였다(§5-4): `exec` 세션을 `codex resume <session-id>` 가 이어받고, bracketed paste
  주입과 작업 중 `Ctrl+C` 인터럽트가 된다. 다만 **claude 에 없는 요소가 하나 있다** — TUI 가
  부팅하며 디렉터리 신뢰 대화상자를 띄운다(`ensureCodexHome` 이 config 를 격리하므로 신뢰
  상태가 상속되지 않는다). 자동 응답으로 넘기든 `config.toml` 에 미리 심든 그 결정이 하나 더
  붙으므로, claude 경로가 안정된 뒤 별도 페이즈로 다룬다. `CODEX_HANDOFF_REJECTION` 은 그때
  함께 걷는다.
- **도는 턴에 새 메시지를 주입해 방향을 바꾸는 것.** 하네스가 지원하지 않는다 — 턴 도중 들어온
  입력은 **큐에 담겼다가 다음 턴**으로 돈다(2026-09-08 실측, `--input-format stream-json` 에서
  턴1 완료 뒤 새 `system/init` 이 뜨고 그제야 두 번째 메시지가 처리됐다). TUI 도 같다. 사람이
  얻는 것은 `Ctrl+C` 로 끊고 새로 지시하는 길이다.
- **스레드 상주 PTY.** 3-2 에 채택하지 않은 이유가 있다.
- **동시 턴 상한.** `2026-09-08-mention-turn-parallelism-design.md` §4-6 의 결정을 그대로 둔다.

## 7. 위험

- **부팅 대기가 이 설계의 가장 얇은 곳이다.** 조건 기반으로 짜도 TUI 의 화면 표시가 버전마다
  바뀔 수 있다. 상한을 넘기면 조용히 넘어가지 말고 실패로 끝내야 그 변화가 드러난다.
- **에코는 화면(ring)에는 남는다.** tail 판정을 버리므로 오판 경로는 닫히지만, 사람이 보는
  화면에 프롬프트 본문이 그대로 뜨는 것은 정상 동작이다(TUI 가 대화를 보여 주는 것이다).
- **codex 와 claude 의 실행 모델이 P5 까지 갈린다.** 그동안 `stdinFile` 경로와 주입 경로가 함께 산다.
  `composeSpawn` 의 `#380` 절이 그 두 세계의 근거를 이미 적고 있으므로 지우지 않는다.
